A chat's permissions are controls, not a status list (COD-168). The worker dialog's **Quyền / Permissions** tab and the chat Details **Quyền công cụ / Tool permissions** section render the same component: three switches (read attached sources, check data, read and search the web) and one dropdown for the working folder with four levels: no folder, read files only, read and edit files, read, edit files and run commands. The levels are cumulative because the grant schema refuses `write` without `read` and `execute` without `write`, so those four are the only grants core can hold. The granted folder's name sits under the dropdown. Choosing a level opens the native picker; choosing no folder revokes. A blocker is never a third position on a control: a Demo worker, a model with no connection, or a grant still loading disables the controls and one short line says why. A team chat keeps its controls when only some members are blocked and names them. The worker dialog's tab acts on that worker's own chat. Before the first message, the switches and the folder in that tab and in Details set what the chat will start with (COD-178, COD-186): the core keeps the set under the worker or team (`Workspace.newChatCapabilities`) and the picked folder beside it (`Workspace.newChatWorkspace`, keyed the same way; the renderer sees only its name and level), and `createTask` moves the set onto the row it creates and turns the folder into that row's grant in the same transaction. The folder is checked again at that moment: it must still exist, be a directory and be the same directory that was picked (the identity check that catches a folder replaced at the same path). If it is not, the chat still starts, without a folder, and the first run's activity says so. The entry is used up either way; choosing no folder or deleting the worker or team drops it. The runtime remains authoritative: it intersects the run's frozen capabilities with current task capabilities and validates the current folder grant again before each operation. Skills, knowledge, packages, teams and routines never grant file or network access.

Workers can read attached sources and reviewed skill resources. With a separate workspace grant, they can list, search, read and edit files in a private working copy, create folders, move, rename and delete files there, and run commands when granted execution permission. Details contains the workspace controls and a separate web permission. Demo does not execute these tools.

The core keeps tool declarations, argument schemas, required capabilities and execution limits in one catalog. Every model call is checked against the tools allowed for its run stage and permissions. A planner with a granted workspace can list, search and read its private copy before assigning file ownership, but cannot write, run commands or use the web at that stage. A planner cannot skip planning by calling the normal reply tool. Instructions and imported skills cannot grant permissions.

`react_to_message` records or removes a named reaction against a committed message ID in the current chat. Core checks the current run, actor and message scope at execution, and refuses a worker's own message; a scheduled run is not offered the tool. A one-shot CLI harness answer carries the same calls as a `reactions` array of at most three `{ messageId, emoji }` items (COD-216). It is idempotent across tool-call replay, needs no file or network grant, and cannot start an agent. User reactions use a separate typed command and also never dispatch a run. `reviseTask.replyTo` carries a saved message ID; core verifies it belongs to the same chat and gives the next worker a bounded excerpt. Neither interaction turns quoted content into instructions or permissions.

`request_user_decision` is available to a team planner and a solo worker in the tool loop. It pauses the current run with one question and two or three choices; the answer enters the saved checkpoint and resumes that same run. Core stores the question and answer with the chat turn, allows at most two questions per turn, and rechecks the original permissions on resume. The answer itself never grants a tool. A backup keeps the decision history but excludes the checkpoint, so a pending question restored from backup is marked interrupted rather than offered as resumable.

`record_work_frame` lets a solo worker or team planner save one short goal, constraints the user stated, unconfirmed assumptions, and intended checks in the run snapshot. Details displays these separately; planned checks do not count as completed checks or evidence. A second record for the same run is rejected. The record does not change grants, assignments, or the user request. It is available through the API and tool-loop CLI paths, but source-only CLI sessions cannot call it.

When a user revises a running chat, core validates and saves the new revision before signalling cancellation to the old run. The new revision waits for the old run to stop; cancelling it while it waits prevents dispatch. Restart recovery leaves that saved revision interrupted for the user to inspect and resume. It never replays an uncertain prior tool call. Existing workspace integration, hash checks, and grant checks still govern effects of both revisions.

Chat command status is derived from the persisted workspace process records for the current turn. Exit code 0, failures, unfinished processes, file conflicts and uncertain calls have separate counts. The compact line may cover only the latest 100 records; Details carries the full available inspection and recovery path. A model's planned check text does not change these counts.

OpenCode Zen and OpenCode Go workers are API workers: Orglet sends its own tool definitions over `/chat/completions` and runs every call through the same core handlers, capability defaults and folder grants as OpenAI or OpenRouter workers. They get no OpenCode CLI, no auto-approve flag and no skill scripts, and cancelling aborts the HTTP request. Fixture tests (`tests/integration/opencode.test.ts`) cover this; no live OpenCode call has been made.

Assigned team members also have send, read and acknowledge tools for the [team mailbox](team-chat.md#worker-messages). These validate membership and the current turn at execution. They do not grant file or network access. API workers and the CLI tool bridge use the same mailbox handlers.

If a worker mistypes a team-message recipient ID, core returns the current assignment's valid recipients as a tool error. The worker can correct the call in the same run; the rejected message creates no mailbox event or new agent. Core still checks the recipient again when it saves a valid message.

For a structured check of a workspace command, the worker may cite the process ID returned by `workspace_start_process`. Core accepts it only from the same run after the process exits, with exit code zero for a pass or nonzero for a failure. The backup retains only the cited process ID, run ID and exit code, not the command or its output. Imported source and dataset checks keep their separate source/checker citations. An assessed workspace check without either source or process evidence becomes `not_assessed` with an explicit limitation, so a missing citation does not discard completed file edits or become a false pass.

If a member reports that its own check passed but an upstream report still lacks evidence, core retains the completed work and changes its overall review recommendation to insufficient evidence with a visible limitation. A report cannot silently turn an unfinished upstream review into a ready recommendation.

A successful `workspace_read` returns an `evidenceId` for that file's current hash. A finding about a workspace file cites that ID in `workspaceEvidenceIds`; this is separate from imported `sourceIds`, which never grants file-edit access. Before saving a report, core checks the read call was committed in the same run, the grant revision is still current, and the file in the private working copy still has that hash. If a worker edits the file after reading it, it must read the file again. Forged, cross-run, incomplete, changed and revoked references fail. A workspace observation without a citation remains an explicitly unverified limitation, so a blocked QA result is not silently promoted to success.

The report and backup keep only the cited read ID, relative path, hash, call ID and grant identity/revision. They omit local absolute paths, file bytes and the tool journal. Details shows the recorded path and hash; it labels a missing or revoked grant and does not claim the current host file still matches the historical read. Restoring a backup does not restore the workspace grant or make the citation a new permission.

The team lead can resolve a pending question or blocker with a recorded decision, or reassign unfinished work to a member whose configuration was frozen at the start of the turn. Reassignment keeps the original dependencies and writable resources, intersects both workers' permissions, and allows at most two attempts per assignment. The two-question limit also follows the assignment when its worker changes. Closing a message does not complete failed work.

The lead receives assignment states and committed artifact identifiers, including when every initial attempt failed. A recovered prerequisite lets waiting dependents continue. Failed attempts remain in history; unresolved questions and blockers remain in the final report's limitations. Fixture tests cover this recovery path and exporting and restoring its history. Fixtures cover interrupted lead decisions before journal commit, pause and resume after a recovered prerequisite, and cancellation before dependents start. They do not prove a live provider or CLI session.

Mailbox calls also use a durable execution journal. A committed output is returned on replay without running the operation again. Interrupted calls retain an uncertain outcome; only reads and operations explicitly implemented as idempotent may run again. Other effects require reconciliation first. A new run or call ID cannot bypass an unresolved effect in the same task. Recovery reads remain available. The journal stays local with checkpoints and is excluded from exported backups.

`TaskInput.toolCapabilities` optionally limits a task to `source.read`, `dataset.check`, `skill.read` and `network.web`. An empty list allows answers but no resource tools. Omitting the field preserves the existing source, dataset and skill capabilities supported by the connection; it never grants network access. CLI defaults allow source and skill reads. Explicit dataset or web capabilities use the core tool bridge, as do workspace and team runs. Standalone source-and-skill-only CLI runs retain their restricted one-shot path. The existing configured preflight is a separate core check, not a harness tool.

A run freezes its capabilities and folder grant the moment it first starts, together with its context (COD-178). Member and synthesis runs of a team turn are created when the message is sent but start later, so a permission granted while the lead is still routing reaches them; a run that already started keeps its snapshot, a resume keeps the snapshot it ran with, and a reassignment attempt keeps the intersection recovery gave it. The effective permission is the intersection of that snapshot and the task's current permissions. The typed `setToolCapabilities` command changes the task policy, or, with a `workerId` or `teamId` instead of a `taskId`, the set a chat that has not started yet will begin with; reducing permissions cancels active work, including opaque CLI processes. Increasing permissions does not upgrade a run that already started. The same rule holds for the folder (COD-186): granting a folder where the chat had none, or raising its level on the same folder (read, then edit, then run commands), stops nothing. A raised level keeps the grant's id and revision, so a run that froze the narrower grant stays valid with what it froze, and the member and report runs still queued pick the wider grant up when they start. Another folder, a lower level or no folder is a new grant or a revocation and stops active work, since a worker may be mid-edit in the old copy. Details exposes the web permission; source, dataset and skill capability restrictions remain available through the core interface.

In a chat, open its menu and choose **Details → Tool permissions**, or open the worker's setup and its **Permissions** tab for that worker's own chat; an empty chat has the same controls, and what is chosen there is what its first message starts with. Under **Working folder** choose **Read files only**, **Read and edit files**, or **Read, edit files and run commands**; the native picker opens and states the requested access, and the folder's name sits under the dropdown. Choosing **No folder** revokes and stops active work; raising the level on the same folder does not. **Read and search the web** is a separate switch. Demo shows these controls disabled with the reason. New permissions apply to every run that has not started yet, including the member and report jobs still waiting in the current turn; a run already working keeps what it started with, so send a new message to give it more.

Reads recheck permissions after IO and before another model request or report commit. Read tools have a 20-second deadline; dataset tools have a 25-second outer deadline and retain the checker's own process limit. Cancellation prevents a late result from entering context; a filesystem read already in progress may still finish internally. Harness processes retain their existing 15-minute deadline and process cancellation.

Harnesses receive only source copies and skill resources permitted by the task. Their existing restricted launch flags remain in place. Orglet cannot intercept each internal CLI file read; a permission reduction terminates the run rather than trying to reconfigure a live CLI. Already dispatched content cannot be recalled.

Backups retain historical run snapshots but restore task and routine capabilities as an empty list. Restoring a backup never grants tools or workspace access on this computer. Workspace write and execution access are separate from source and network capabilities.

## Proposing app changes

A worker can be asked, in its own chat, to set the app up: "tạo cho tôi một crew nghiên cứu 3 người", "make this crew a template", "write a skill for code review", "schedule this every Monday 9:00", "switch to dark mode and SF Pro" (COD-199). It cannot do any of that itself. What it has is six proposal tools, each of which stores one **proposal**: a card in the chat turn that the user applies or dismisses. This is setup help on the user's request, not an agent running the workspace: a proposal comes from a message the user wrote, waits for the user's click (or the per-orglet switch below, which the user turned on), and applies through the same commands and validation the dialogs use. It stays inside product.md's line on company simulation and autonomous agents.

| Tool | Proposes | Arguments (all present, `null` leaves a field alone) |
|---|---|---|
| `propose_orglet` | Create an orglet, or edit one (`targetId`) | `ref`, `name`, `description`, `instructions`, `provider`, `modelId`, `skillId` or `skillRef`, `taskBudgetMicros`. Create needs `name` and `instructions`; `provider` null means the proposing worker's provider and model, `skillId` null its skill. |
| `propose_crew` | Create a crew, or edit one (`targetId`) | `ref`, `name`, `instructions`, `memberIds` and `memberRefs` (up to eight together), `leadId` or `leadRef` (default: the first member), `workflow` (default parallel), `monthlyBudgetMicros` (default $5), `taskBudgetMicros`. |
| `propose_crew_template` | Export a crew as a template file | `teamId`, or `teamRef` of a crew proposed in the same reply. Applying asks where to save the file. |
| `propose_skill` | A new skill, or a new revision of one (`targetId`) | `ref`, `name`, `content`. An imported skill package cannot be edited this way. |
| `propose_schedule` | Create a routine, or edit one (`targetId`) | `name`, `brief`, `frequency`, `time`, `weekday` (default Monday), `timeZone` (default this computer's), `workerId`/`workerRef` or `teamId`/`teamRef` (default: this chat's orglet or crew). A routine is saved switched off, whether created or edited; enabling it is the user's approval, as today. |
| `propose_settings` | App settings | `theme`, `language`, `accentColor`, `logoColor`, `interfaceFont`, `codeFont`, `copyFormat`, `downloadFormat`, `autoTitles`, `confirmOpenTask`. |

The schemas live in `apps/desktop/src/shared/app-proposals.ts` and are strict: a field for an API key, a connection, a harness account, a backup or restore, an erase, a tool permission, a working folder, a budget cap or the auto-apply switch is an unknown key and the call is refused. Every model call is checked the same way as any other tool (`assertToolCall`), so a harness cannot smuggle one in either. `tests/integration/app-proposals.test.ts` asserts the refusals.

A chat on a CLI harness (Claude Code, Codex, Cursor Agent, Gemini CLI) with no working folder, web or data checks does not run the tool loop: it is one CLI call with a JSON schema. There the same proposals travel inside the answer (COD-206): when the run may propose, the answer schema carries an optional `appProposals` array of `{ tool, arguments }` items, `tool` one of the six names and `arguments` that tool's argument object, and the prompt explains the field in the tool descriptions' words. Claude Code gets it in `--json-schema`, and Cursor and Gemini CLI in the schema embedded in the prompt (the item union is `anyOf`, which Claude Code's structured outputs accept); Codex keeps its one-string envelope, so the item schema goes in the prompt and `appProposals` sits in the payload JSON. After the answer parses, core feeds the items in order through the same `record` the tools use, so refs between items keep working. An item the worker got wrong (an unknown tool, arguments off the schema, a missing name, an unknown ref) becomes a limitation of the saved answer, the other items are still stored, and the run completes. Since Orglet cannot see which of the copied sources the CLI opened, a run with any attached source counts as having read untrusted content and its proposals wait for a click, auto-apply or not.

The tools are behind the capability `app.propose`, which a chat has by default and which the worker dialog's **Quyền / Permissions** tab and the chat Details show as the switch **Đề xuất thay đổi trong app / Propose app changes**, beside the other three. Like them it is frozen per run and intersected with the chat's current set. It is never offered to a plan run (the lead routes, it does not set the app up) or to a scheduled run (`task.routineId`), whatever the capability set says. The turn's brief message carries an `appChanges` field listing the live orglets, crews, skills and schedules by id, the providers already in use, which chat this is and the current values of the settings above, so the worker can name existing things. A proposal that gets something wrong (a missing name, an unknown id, a change that changes nothing) goes back to the model as the tool's answer and the run goes on; it is not a failure.

A reply may carry several proposals that build on each other: a skill, an orglet that uses it (`skillRef`), a crew of orglets proposed just before (`memberRefs`), a template of that crew (`teamRef`), a schedule for it. A `ref` is a short handle the worker gives a new orglet, crew or skill, unique within the run, and is resolved at apply time: applying a card whose reference has not been applied yet fails with "Áp dụng đề xuất … trước", so the cards are applied in order, and **Áp dụng tất cả / Apply all** does exactly that.

**What the cards look like** (COD-212). The new orglets of one reply share one card: a row each with its face (the mascot suggested for its name and description until it exists, then the orglet's own; orglets proposed together avoid the faces and colours the other orglets and the earlier rows already show when a close match exists, COD-265), its name, its one-line description and its model as a small chip (the provider's name, plus the model id when one is set). A row's right side is its state (applied, dismissed, waiting for a click) or its own Apply and Dismiss; with two or more rows pending the card ends with **Áp dụng N Tí / Apply N orglets** and **Bỏ qua N Tí / Dismiss N orglets**. Clicking a row opens a dialog with the full fields (instructions at full length, skill, limit, model) and the same Apply / Dismiss; once the orglet exists, the row opens it instead. A new crew is drawn as its people: the members' faces and names in a row, the lead wearing a small crown, then chips for how it runs (sequential or parallel) and what it may spend. Every other card (an edit, a skill, a schedule, settings, a template) keeps its title and a field list, before → after for an edit; a schedule reads in words, such as **Weekly on Monday at 09:00 · Asia/Saigon**. Values are shown as names, never ids: a skill by its name, a provider by its name, and a `ref:` to something proposed in the same reply by that proposal's title, or by the real orglet's name once that proposal was applied (`renderer/components/proposalValues.ts`, checked by `tests/integration/proposal-values.test.ts`). **Áp dụng tất cả (N) / Apply all (N)** under the turn's cards stays for a reply that proposes more than the orglets, and applies in the order proposed, so the orglets land before the crew that names them.

Proposals are rows of `app_proposals` (schema version 15), keyed by chat and run, deleted with the chat, and not part of a backup: a backup restored elsewhere has no cards to apply and no record of automatic applies. Each row keeps the validated arguments plus the defaults filled in when it was made, the card's title and lines (the fields a creation sets, or before → after for the fields an edit would change), a hold, a status (`pending`, `applied`, `dismissed`), and after Apply the outcome: when, whether it was automatic, what it created or changed (so the card can open it), an undo record for an automatic apply, or the plain error, which leaves the card pending so it can be tried again. `TaskDetail.appProposals` carries them to the thread. The commands are `applyAppProposal`, `dismissAppProposal` and `undoAppProposal`; Apply calls `saveWorker`, `saveTeam`, `saveSkill`, `saveRoutine`, the settings writer or the template exporter through the core service, so a skill edit is a new revision, an in-flight run keeps the snapshot it started with, and nothing a dialog would refuse gets through.

**Auto-apply.** A worker's Permissions tab has one more switch, **Áp dụng thay đổi trong app mà không cần hỏi / Apply app changes without asking**, off by default and saved on the worker like its other fields (`autoApplyProposals`, a revision like any edit). When it is on, the run's safe proposals are applied the moment the run finishes and its answer is saved (`Runner.commit` → `AppProposals.finishRun`), never mid-run, in the order they were made; the card says **Đã áp dụng tự động / Applied automatically** and offers **Hoàn tác / Undo** where a command exists to take it back: a just-created orglet or crew is deleted if nothing uses it yet, an edited orglet, crew or skill gets its previous fields saved again as a new revision, and settings get their previous values. A created skill or routine has no undo, because the app has no delete for them. The proposal tools cannot set this switch; a template's workers never carry it.

**Never automatic.** A proposal keeps waiting for a click, and the card says why, when it raises a spending limit (an orglet's or crew's limit per task above the current one, or above the proposing worker's own cap for a new one, a crew's monthly budget above the current one or the $5 default), when it needs a save location (a template), or when the run took in anything nobody vetted: a web page or search, a workspace file, an attached source, another worker's message or report. The runner keeps that list on the checkpoint (`untrustedInputs`, so a resumed run remembers) and applies it to every proposal of the run at the end, including ones made before the read. Deleting or archiving, editing another orglet's permissions, granting a folder and raising tool permissions cannot be proposed at all. A worker's one-sentence change to its own instructions after repeated feedback (`propose_self_improvement`, hold `self`) also always waits for a click; see [self-improvement.md](self-improvement.md).

## MCP tools

An orglet the person allowed to use an MCP server gets that server's tools in the same tool loop, named `mcp__<server>__<tool>` (at most 64 characters). The list is frozen when the run first starts, like its permissions, and is never offered to a lead's planning step, a scheduled run or Demo. Every call is checked against that frozen list (`assertToolCall`), then against the chat's standing MCP permissions (`Task.mcpGrants`). A call the chat has not allowed stops a solo chat the way `request_user_decision` does: the checkpoint keeps the call, the chat shows an approval card (allow once, always this tool, always this server, refuse), and the answer resumes the same run, which then runs the call or hands the refusal back. A crew or group run cannot hold the turn, so an unallowed call comes back refused. Results are untrusted data capped at 24,000 characters; a call has a 60-second deadline and cancelling the run cancels it on the server. Calls go through the tool journal: a tool the server marks read-only may replay after a crash, any other interrupted call is an unknown outcome to review in Details. A result counts as unvetted input, so an app change proposed after it waits for a click. MCP servers are not workspace commands: they can use the network, and adding one gives workspace commands no network access. See [mcp.md](mcp.md).

## Orglet's browser

A chat with `browser.read` gives its runs seven browser tools (`browser_open`, `browser_snapshot`, `browser_find`, `browser_screenshot`, `browser_scroll`, `browser_tabs`, `browser_close`) that read pages in a Chrome or Edge window Orglet starts with its own profile. The run freezes the profile when it starts, like its other permissions; every call is checked against the capability, the frozen profile and the chat's site list as it is now (narrowed to the main chat's for a side thread), and journaled in `browser_actions` with a core-set risk. A browser host process drives the browser through `playwright-core`, and a proxy in that process checks every connection, redirects and frames included. Snapshots count as untrusted input, only the latest stays whole in later steps, and a run with the browser gets 16 model steps. Crews and schedules may use it; a schedule's profile and site list are part of what saving it approves. See [browser.md](browser.md).

`browser.act` (the **Read and act** level, which needs `browser.read`) adds five tools: `browser_click`, `browser_type`, `browser_select`, `browser_press` (Enter, Tab, Escape, the arrows, PageUp, PageDown, Home, End, Backspace) and `browser_wait` (up to 5 seconds). They name an element by the ref of the latest snapshot. Before each step the host takes a fresh snapshot and reports the element and the page; the core sets the risk (`browser-risk.ts`): **input** runs at once, **consequential** (a POST form, Enter where it would send, a file picker, a download, a name like send, pay, buy, order, delete, post, confirm, sign out or their Vietnamese words, a password, payment or CAPTCHA page) asks the person in a solo chat and is refused in crews, group chats and schedules. Typing into a password or card field, or anything on a page with a CAPTCHA, is refused outright. The model's arguments carry no risk. An acting step goes through the tool journal: input may run again after a restart, a consequential one never does. A schedule is never given these tools, and a run with them gets 24 model steps.

## Public web tools

Workers with explicit `network.web` permission can read a URL or search the web. The permission is frozen per run, checked before and after IO, and checked again before sending cached content to a model. Revoking it cancels active work. It does not grant network access to workspace commands or make fetched content an editable file. A search the service blocks, or a page that cannot be fetched, comes back to the worker as a tool error it can work around (another query, or a known URL); it does not fail the run. A run with web access gets 16 model steps instead of the 6 a sources-only run gets, so it can search, read a few pages and still write its answer. Because every step resends the whole conversation, pages read before the latest two are cut to their first 1,500 characters before each step, keeping address, title and provenance; the worker can read a page again when it needs the full text (COD-183; see the [technical guide](technical-guide.md#local-harnesses-claude-code-codex-cursor-agent-gemini-cli) for the measured saving). Search results and source reads are not cut.

URL reads use public HTTP/HTTPS addresses on default ports. Core rejects credentials in URLs, private and special-purpose IP ranges, mixed public/private DNS answers, and redirects to forbidden destinations. The socket uses the checked IP while TLS verifies the original hostname. At most three redirects are followed; HTTPS cannot downgrade to HTTP. Requests use no browser cookies, provider keys or proxy configuration. JavaScript and linked resources do not execute or load.

Each call has a 30-second deadline, a 1 MiB response limit and a 24,000-character text limit. A page longer than 1 MiB is read up to the limit and marked truncated, with a coverage line saying only its first 1 MiB was read (COD-266); unsupported formats and interruptions fail explicitly. Successful reads include the requested URL, final URL, redirects, fetch time and truncation status. Content remains untrusted data, including any instructions it contains. Committed tool outputs are journaled for resume and are never registered as writable workspace files.

### Web search

Search goes to the provider picked in **Settings → Web search**: Exa, the default for new and existing workspaces, or DuckDuckGo (COD-266). The switch under a chat's **Details → Tool permissions** names it ("Search with Exa, read public pages"), and every result says which provider answered. Only the query leaves the machine: the search tool is handed nothing but the parsed query, so no chat text, file content or user identifier can reach the provider. It returns up to ten results with the provider, its URL and the fetch time; each has a title and a public URL, and Exa's also carry a short excerpt Exa picked (at most 300 characters). Results are untrusted data like any page. The target pages are not fetched; a worker must read them before citing their contents. Queries must not contain secrets or private workspace content.

**Exa** is Exa's hosted MCP server, `https://mcp.exa.ai/mcp`, called with the MCP SDK's Streamable HTTP client. Every request of that client goes through the same boundary as a URL read: a public HTTPS address checked and pinned, the 1 MiB limit per response, the call's 30-second deadline and cancellation, no cookies, no proxy configuration and no redirects. Only POST and DELETE go out; the SDK's standing event stream (a GET) is answered locally with 405, since a search needs no message from the server. One search is one short session: the MCP handshake (protocol version and the client name "Orglet"), one `web_search_exa` call with the query sent as both `query` and `objective` (the hosted tool requires an objective) and `numResults: 10`, then a DELETE that ends the session. With a key saved, each of those requests carries it as the `x-api-key` header; without one, none does.

Without a key, Exa's search is free and rate-limited by network address. Exa's docs give no number. On 2026-09-26 this machine was refused with HTTP 429, `x-ratelimit-limit: 0` and a `retry-after` that ran to midnight UTC, so the free searches can run out for the rest of the day. An Exa key lifts that; its searches count against that Exa account (about $7 per 1,000 searches after Exa's monthly free credit, on Exa's pricing page on 2026-09-26). Exa offers zero data retention only as an enterprise add-on, so assume it keeps the queries it gets.

**DuckDuckGo** reads DuckDuckGo's non-JavaScript results page the way a URL read does, with the query in its address, and returns up to ten links without excerpts. It often answers an app with a human-verification page.

A failed search never switches to another engine. The worker gets a plain error it can act on, and the chat shows it: Exa's free searches are rate-limited (with the wait when Exa says, and where to add a key), the saved key was rejected, the key itself is rate-limited, Exa could not be reached, Exa returned an HTTP error, or the answer was neither results nor "no results". A DuckDuckGo challenge or unreadable page is a failure too, never an empty search. **Settings → Web search → Test** runs one real query ("Wikipedia") through the saved provider and shows the first result's title or the same error.

The Exa key is encrypted with the system's secure storage by main (`search-exa.credential`, beside the API key files) and read by the core only when a search is about to go out. The window only learns whether one is saved, and the key is not in the database, backups, templates or logs; erasing data leaves it, like the API keys.

Normal tests use DNS/HTTP fixtures and a local HTTP server to check redirects, address restrictions, byte limits, cancellation, provenance and revocation through Runner. The Exa exchange is tested against a fake network that answers the way Exa's server does and against a real MCP SDK server over the production HTTP transport (`tests/integration/web-search.test.ts`): result mapping, the key header only when a key is saved, nothing but the query sent from a chat holding private text, each error, cancellation and the byte limit. To test the external services without credentials, set `ORGLET_TEST_WEB=1` and run `pnpm exec vitest run tests/integration/web-tools.test.ts -t "public web smoke"`; its search goes to Exa without a key, so it fails with the rate-limit message once this machine's free searches are used up. External availability is separate from the passing fixtures.

## Windows isolation backend

Workspace access is separate from attached sources. The native folder picker records a task-specific grant with read, write and command permissions. Its title states the requested access. The renderer receives only an opaque ID and folder name; it cannot submit an arbitrary directory through the command bridge, for a chat row or for a chat that has no row yet. Runs freeze the grant ID, revision and permissions. Replacing or revoking a grant cancels active work and invalidates old snapshots; widening the same grant keeps its ID and revision and cancels nothing. Core also checks the directory identity to detect replacement at the same path, including for a folder kept for a chat's first message.

These grants persist only in the local database. Exported backups retain historical snapshots but contain no directory grant or local path. Restoring those snapshots grants no workspace access. The bridge, storage, Details controls and model dispatch are connected. Claude Code, Codex, Cursor and Gemini CLI return structured tool requests to core, which checks the advertised tool, schema and current permissions before execution. Fixtures exercise each harness through this path. Native CLI configuration and containment still need verification with installed harnesses; the bridge alone does not establish that their internal tools are disabled.

The workspace runtime uses Microsoft's MXC executor, pinned to SDK 0.8.0 with config schema 0.8.0-alpha. The executor is bundled separately from the app archive on Windows x64. Native capability probing must confirm BaseContainer before launch; other platforms and missing support fail closed. A separate execution grant is required for model command tools.

Only the working directory is writable. Explicit runtime directories are readable; parent folders and the host environment are not inherited. Network egress, ingress and host loopback are denied. DACL mutation fallback is disabled. The Node runtime needs isolated UI initialization, but clipboard access and input injection remain disabled.

Output is capped at 256 KiB across stdout and stderr. Commands have a maximum two-minute deadline; abort, timeout and excess output kill the executor and its BaseContainer job. The native smoke checks writes, outside-file and junction denial, environment isolation, loopback denial, output limits and descendant cancellation with synthetic fixtures.

Run `pnpm test:isolation` on a supported Windows host, or `pnpm test:isolation --packaged` after `pnpm build` to check the bundled executor. Ordinary `pnpm test` runs the policy fixture and skips the native cases; that is not evidence of native containment. See the [MXC SDK documentation](https://github.com/microsoft/mxc/blob/main/sdk/node/README.md) for the public-preview status and platform requirements.

The bundled workspace helper can list files, search literal text, read UTF-8 in pages and edit a private copy against an expected SHA-256 hash. Read offsets count Unicode characters, so a page does not split an emoji or Vietnamese character. Creating a file requires it to be absent; replacing one requires the hash from a prior read; missing parent folders are created. The user directory is not changed by these private-copy operations.

With **Read and edit files** (or higher) the helper also creates folders, moves or renames files and folders, and deletes files and empty folders in the copy (COD-254). Before this, an orglet asked to tidy a folder could only answer that it had no way to do it.

| Tool | Arguments | In the private copy |
|---|---|---|
| `workspace_create_folder` | `path` | Creates the folder and any missing parents. A folder already there is left as it is; a file with that name is refused. |
| `workspace_move` | `from`, `to` | Moves or renames a file or a whole folder. `to` must be free; only a change of letter case may name the same entry. Missing parents of `to` are created. A folder cannot move inside itself. |
| `workspace_delete` | `path` | Deletes a file, or a folder that is already empty. A folder with anything in it is refused: move or delete what is inside first. |

Each path goes through the same checks as a write: relative to the copy, no `..`, no `.git` or `.orglet-*` part, no Windows device name, and no link anywhere on the way. A refusal the worker can fix (the new path is taken, the folder is not empty, the name is a file) comes back as the tool's result with a hint, like a missing path (COD-190), so it does not end the run or leave an unknown outcome in the journal; the run's activity says what was refused. Team members follow their assignment's `writeResources` for both ends of a move; a new folder may also be a parent of an owned path, since writing an owned file creates its parents. Every change to the copy (a write that changed a file, a new folder, a move, a deletion) counts as a file change for the command rule below.

Snapshots record file hashes, folders and omissions, with limits of 1 MiB per file, 100 MiB total and 10,000 entries. Links, `.git`, internal `.orglet-*` paths and `node_modules` are omitted. Limits fail explicitly; a partial snapshot is not presented as complete. `--packaged` also tests the helper with both Node and the packaged Electron runtime.

Each run retains its own copy and baseline hashes in local storage. Operations on that copy are serialized, and team writes must fall within the assignment's `writeResources`. Workspace tools have a 150-second outer deadline, including the first snapshot; subsequent helper operations have a 30-second process deadline. Workspace runs have at most 40 model steps and retain the existing budget and checkpoint checks. Two steps before any run's limit, the worker is told to stop using tools and hand in what it has (what changed, what was verified, what is not finished), and only the tools that end a run stay available, so a long coding run ends with its work rather than failing at the cap. A crew member is also told that what it found is its result: its report reaches the lead as a finished assignment marked as cut short, and only a missing required file change still makes it a blocker (COD-256). Reads and effects recheck current permission; revocation prevents cached workspace content from being sent in a later model request.

When a `submit_report` call fails schema validation, the activity journal records only field paths and validation codes. The runner gives the model one correction request using committed tool outputs, with only `submit_report` advertised; it cannot repeat a workspace write in that correction. Invalid report bodies are not saved in the checkpoint or activity event. A second malformed report ends the run with the field-level reason.

When the selected folder contains `.git`, core creates a private repository and detached worktree from the snapshot. The baseline includes current uncommitted and untracked files within the snapshot limits. It does not copy repository history, settings or hooks, or alter the original index. Each worker has its own repository and worktree; integration still checks the original file hashes in order. Git for Windows must be installed at the configured runtime location. Missing Git fails explicitly.

Preparing Git metadata is a fixed core operation, before the working directory reaches a worker. Core invokes only fixed Git plumbing commands with a clean environment, disabled hooks and filters, and no network protocols. Commands start in the fresh metadata directory rather than the snapshot, preventing executable lookup in project files. This preparation has a two-minute deadline and supports cancellation. Agent-requested commands continue to run in BaseContainer; they do not receive this internal Git operation or its runtime access.

## Integrating a file

The Windows integration broker (`apps/desktop/native/WorkspaceIntegrate.cs`) accepts one step at a time as JSON on stdin, never a shell command, and it is the only code that changes the person's folder. For every step it locks the root and each parent directory (deny write and delete sharing), opens what it changes with reparse points not followed, checks the handle's final path, and refuses hardlinks. It changes the file or folder **through the handle it checked**, so what was hashed is what is changed. The five steps:

| Step | What the broker does | A conflict when |
|---|---|---|
| `write` | Replaces an existing file whose bytes still have the snapshot hash, after flushing its original bytes to a private backup; or creates a new file with create-new semantics, creating missing parents. | the file was edited (`changed`), removed (`missing`), or a file appeared at a new path (`exists`) |
| `create_folder` | Creates the folder and missing parents; one already there as a folder is fine. | a file has that name (`exists`) |
| `move` | Opens the source exclusively with delete access, checks its hash, then renames that handle (`FileRenameInfo`, never replacing). The file keeps its identity, times and streams; nothing is copied. Missing parents of the target are created. Changing only the letter case renames in place. | the source was edited (`changed`) or removed (`missing`), or something is at the target (`exists`) |
| `delete` | Opens the file exclusively, checks its hash, flushes its bytes to a private backup, then marks that handle for deletion. | the file was edited (`changed`) or removed (`missing`) |
| `remove_folder` | Marks the folder for deletion through its handle. The file system checks emptiness at that moment and refuses new entries in a folder marked for deletion, so nothing can slip in between. An empty folder needs no backup. | anything is in it (`not_empty`), or it is gone (`missing`) |

A conflict returns the reason and changes nothing. A file in use by another program, a junction, a hardlink or a path that resolves elsewhere is `blocked`, also with nothing changed. Before invoking the broker, core saves the execution journal entry and reconciliation metadata (the step, both paths of a move, the expected hash, the backup location). A crash or invalid result leaves an uncertain operation that cannot replay automatically; the saved original remains available even if the process stopped after writing or after the backup of a deletion.

**The plan.** Before publishing a worker's final answer, core inventories the private copy through the sandboxed helper and compares it with the snapshot (`core/tools/workspace-plan.ts`). It never trusts what the worker says it did, so a rename done by a command counts the same as one done with `workspace_move`. Paths compare without regard to letter case, as Windows does. A file that vanished from one path and appeared at another with the same bytes is a move, which integrates as a rename; when several vanished files share those bytes (duplicates), the one with the same name, then the one in the same folder, is the move and the others are deletions. A file that was moved and edited is a new file plus a deletion. A file whose name only changed case is renamed in place, then edited if its bytes changed. The steps run in one order: new folders (outermost first), moves, writes, file deletions, folder removals (innermost first). What adds comes before what takes away, so a hand-in stopped halfway leaves an extra file rather than a missing one. A path that is a file on one side and a folder on the other cannot be ordered safely, and is refused before anything changes. A copy saved before COD-254 has no folder list; it integrates without folder steps, as before.

Integration runs the steps in order with a two-minute total deadline, and each step is its own journaled broker call. Only a write carries bytes, obtained through the sandboxed helper instead of reading worker-controlled paths on the host. The first conflict or block stops the hand-in: no success artifact is published, the steps already taken and their backups stay recorded, the rest stay pending, and **Details → Files and processes** lists every step with its action (create folder, move, delete, remove folder), its state and, for a conflict, why it stopped. Nothing the person changed, removed or created meanwhile is overwritten or lost. Process output remains readable after a restart.

**Deleted files go to a private backup, not the Recycle Bin.** The broker writes the bytes to `workspaces/backups` in Orglet's app data and deletes the file only after that write is flushed. This keeps one enforcement point that is tested end to end: the Recycle Bin is only reachable through the Explorer shell by path, which would lose the check that the file deleted is the file hashed, and some drives have no Recycle Bin at all. In **Details**, a deleted file has **Khôi phục / Restore**, which puts the backed-up bytes back at the same path through the same broker as a new file: create-new semantics, so whatever stands at that path now is never overwritten (rename or move it and try again). Restore needs the chat to be stopped and to still hold the same folder with edit access, is journaled like any other effect, and is offered until the attempt is retired with **Keep current files**, which takes no new effect. A replaced file's original is backed up the same way but has no restore button yet.

**macOS.** The workspace runtime needs the Windows BaseContainer sandbox and this broker, so on macOS every workspace tool, the new ones included, fails closed as before; nothing here adds a macOS path.

`pnpm test:isolation --packaged` includes concurrent writer, user edit, Unicode path, junction/hardlink and process-crash cases for writes, and for the new steps: creating a folder and writing into it, a move that keeps the file's identity, a case-only rename, a move onto an existing file, a moved or deleted file the person edited or removed, a folder the person put a file in, junctions and hardlinks on either side, and a crash after a deletion's backup. It also runs model fixtures through Runner, the packaged Electron helper and the integration broker: a normal edit commits; an intervening user edit remains unchanged and produces no success artifact; an inbox is sorted into folders with moves, renames, a deleted duplicate (then restored) and an emptied folder removed, and the same run with a photo the person replaced meanwhile stops at that photo with nothing lost. `tests/integration/workspace-handin.test.ts` runs the same tidy-up and every conflict through Runner against a plain-Node stand-in for the broker, on any platform. This is fixture evidence, not a live-provider test. Crash injection is compiled into a separate test executable; the packaged broker contains no crash-test control. The broker is compiled with the Windows .NET Framework compiler during packaging.

## Commands and process results

Execution-enabled workers can start a process, wait for status, read stdout or stderr in pages, and cancel it. The command uses either the bundled Node runtime with literal arguments or Windows cmd with one command string. The user PATH and shell profiles are not inherited; tools such as Python or Git are not implicitly available. In Windows cmd, `node` is the bundled runtime, and `npm`, `pnpm`, `yarn` and `npx` are small stand-ins over it: `npm test`, `npm start`, `npm run <name>` (and the pnpm and yarn forms) run the working copy's `package.json` scripts, npm's `pre` and `post` scripts included, with `node_modules/.bin` on the path, and `npx <name>` runs a binary already in `node_modules/.bin`. They cannot install, update or download packages, because commands have no network; asked to, they say so and exit with 1. What the folder already has installed is there: while a command runs, each `node_modules` next to a `package.json` the working copy started with (up to 16) is linked into the copy at the same place and granted read-only, so tools such as vitest, tsc or eslint and the project's libraries load as usual. A `node_modules` that is itself a link is left out. Commands run Node with `--preserve-symlinks`, because the sandbox does not let Node read the folders above the copy to work out real paths; so that pnpm's linked layout still works, every Node process a command starts preloads a small resolve hook that follows the links inside a granted `node_modules` (and only there) to the real package folder, where its own dependencies sit. Nothing can be written inside it, the link is removed when the command ends, and `node_modules` is never part of what the orglet hands in. Commands have no network access, not even loopback: a server one command starts cannot be reached by another command or by its own process, so status and output results carry a hint that points the worker at in-process testing (see [Commands and loopback](technical-guide.md#commands-and-loopback)).

Starting a process saves its identity before launch and returns a handle. The handle is not a completed result. Output is limited to 256 KiB across both streams; pages contain up to 16,000 Unicode characters. Status can wait up to ten seconds rather than repeatedly polling. While a process runs, file tools and integration cannot access the same working copy. Cancellation waits for the sandbox process tree to stop. Leaving a run, including pause or failure, stops its remaining processes.

Core saves running, exited, cancelled, timeout, output-limit and uncertain outcomes separately from the tool-call journal. After a restart, an unfinished command becomes uncertain and cannot silently launch again. Its task cannot integrate changes or report success until that uncertainty is resolved. A command still running at hand-in blocks too.

Hand-in judges the code the worker hands in, not every command it ever ran (COD-189). Every distinct command (program plus arguments) that started after the run's last file change must have exited 0 on its latest run; a failure there blocks integration, and an unrelated successful command does not hide it. A failure from before a later file change is superseded: it no longer blocks, but the report's limitations name the command and its exit code (or the state of a cancelled or timed-out one) so nothing is hidden. With no file change at all, every command counts. A block only holds something back when there is something to hold: if the copy has nothing to hand in (the plan from its inventory has no step, whatever the worker did in between), a failed or unfinished command does not block (COD-270). The answer is published as usual, and its limitations name each such command with its exit code or state ("A command failed and there were no file changes to apply: npm test (exit code 2)."). For a read-only question such as "run the tests and tell me whether they pass", the failing command is the answer. A command that changed the copy itself, with no file tool, still leaves something to hand in and still blocks. A file change is a `workspace_write` in the run's private copy that changed the file's hash, or a folder created, a move or a deletion there (COD-254). Core does not compare timestamps for this: the copy keeps a count of such changes, and each process record stores that count at start; both writes and command starts are serialized per run, so a command started either before or after each change. Process records from before this rule, which lack the count, still count as current. All outcomes stay in Details and in the chat command status.

**When the rule blocks** (COD-270), which only happens for a copy with changes to hand in. The run still fails and nothing reaches the folder, but it no longer loses the work. The copy stays `ready` with its change counts, and the run keeps a `blockedHandIn` record (`shared/blocked-hand-in.ts`): each blocking command's program and arguments, its exit code or state, and its process id, plus a fingerprint of the copy's files. A solo chat's run also keeps the answer it handed in, exactly as it would have been saved. The turn shows that answer, one line per blocking command ("`npm test` exited with 1, so the changes were not applied") that opens the command's last output lines through `recoveryProcessOutput`, and the changed-files line that opens the diff. It offers three actions. **Apply anyway** sends the `applyBlockedHandIn` command (`{ taskId, runId }`, strict), handled by `Runner.applyBlockedHandIn`. That integrates the copy through the same hash-checked broker, backups and ownership checks, skipping the failed-command rule for the recorded process ids only. It records an event and saves the answer with a limitation ("The user applied the changes even though npm test failed (exit code 1)"). **Ask to fix** puts a reply naming the command and its exit code in the composer without sending it; the next turn starts from the folder as it is, so the orglet redoes the work. **Retry** is the usual retry. No tool offers the override to a model. The command refuses a run that is not the chat's latest, a folder grant that was revoked or narrowed since the run (widening keeps the grant and is fine), a copy that is no longer `ready` or whose files changed since it was blocked, a retired attempt, and a chat that is running. In a crew or a group chat the member's run keeps only the commands: its error card, or the crew's combined answer, names the member and the command, and there is no Apply anyway for one member's copy.

Native fixtures cover Node and cmd execution, descendant cancellation, timeout and excess output. The Runner fixture edits a file, runs a check against the private copy, reads its output and then integrates. A nonzero check exit prevents both integration and a success artifact.

The packaged isolation suite also sends one team request through planning, a private file edit, a native check, mailbox handoff, integration, a dependent review and synthesis. It runs that same flow through an API adapter and the Claude Code, Codex and Cursor tool bridges. Model and CLI responses are fixtures; the workspace helper, command isolation and file broker are real packaged executables. This proves the core dispatch paths, not authentication or native tool restrictions inside a live CLI session.

## Reviewing an interrupted attempt

Open **Details → Files and processes** to inspect saved process output, file change states and calls whose outcome is unknown. Output is paged without restarting the process. Opening Details does not retry an operation.

The section is one row per attempt, newest first (COD-191): the worker, when the attempt started, and what became of its files in plain words (Integrated, Changes not applied: 3 files, No changes, File conflict, Kept current files). Under the row, calls whose outcome is unknown are named by what they did and when ("Write lib/http.js · 09:05 · outcome unknown", "Run node --test"), never by their call id; core keeps the tool name, one safe argument (the path, or the program and its arguments, never file content or a hash) and the time in the journal for this. The attempt's files and its commands fold under a count ("6 commands · 2 passed, 4 failed"); each command opens to its paged output. An attempt whose unknown call, unknown command or conflicting working copy blocks the chat says so in red, and only an attempt that still needs a decision carries **Keep current files**. Retired, integrated and otherwise settled attempts fold behind **Show N earlier attempts**.

When a turn is refused by that guard, the run fails with the code `unresolved_attempt` (not only a message), and the chat's failure card says that an earlier file change has an unknown outcome and offers **Review in Details**, which opens Details scrolled to the blocking attempt. **Retry with current settings** stays available but fails again until that attempt is retired.

After stopping the task and checking the files, **Keep current files** retires the old attempt. The confirmation leaves current files, private copies, backups and historical outcomes unchanged. It does not apply pending edits or restore originals. The old attempt cannot resume or replay tools; a new run can work from the current files. Core rejects a stale review token or a still-running process. Completed runs cannot be retired through this action.

For a changed or moved file, **View private changes** reads the retained working copy through the isolated helper. It requires the original read grant to remain valid and the task to be stopped. Pages are plain text; if the file hash changes between pages, reopen it from the beginning. Inspection does not apply edits or replay tools. The diff viewer under the answer shows the changes side by side; the only backup Details can restore is a deleted file's ([above](#integrating-a-file)).

The packaged smoke checks output paging after restart, cancelling and confirming retirement, and preservation of the failed run and uncertain effects.

Codex launches explicitly disable native web search and local image attachment (`view_image`), and set the project-instruction byte limit to zero. A source-only answer can still see the chat's own images: Orglet attaches its hash-checked copies with `--image` ([PDFs and images](capabilities.md#pdfs-and-images)). Web and file access use the core permission checks; the argument contract is covered by fixtures. These settings follow the [Codex configuration reference](https://developers.openai.com/codex/config-reference/), but are not a claim of live harness verification.

The CLI tool loop retains reported cost estimates in its checkpoint and subtracts them from the next call's allowance. Exhaustion pauses before dispatch, and resuming the same run keeps those estimates. They remain separate from API ledger charges. This is not a team-wide billing guarantee: native CLI budget enforcement varies, and a CLI that omits cost information remains explicitly unknown.

CLI cancellation waits for both process-tree termination and process closure, with a bounded deadline. If either cannot be confirmed, the run fails with instructions to inspect and stop the CLI in Task Manager. Core keeps that call directory for inspection and does not treat the aborted request as a successful cancellation or automatically resume its uncertain checkpoint.
