This guide covers how Orglet runs work, connects providers and harnesses, and what each limit and check does. First walk-through: [Getting started](getting-started.md). For what Orglet is and who it is for, see the [README](../README.md) and [product direction](product.md). The [docs map](README.md) lists the rest.

This build supports individual workers, sequential or parallel teams, native OpenAI, Anthropic, xAI (Grok), OpenRouter, OpenCode Zen and OpenCode Go connections, custom OpenAI-compatible connections, local Ollama, local Claude Code / Codex / Cursor Agent / Gemini CLI harnesses, local dataset checks, routines, checkpoint/resume, backup/restore, team templates, Agent Skills import/review/export and reviewed reusable knowledge. The full MVP in `plans/orglet_mvp_plan_vi.md` is still in progress. Custom metric recomputation beyond built-in exact-match accuracy, live API-provider acceptance (script ready, needs a key path), a clean-machine Setup install and benchmarks remain unverified. The public 0.2.x release ships Windows Setup and ZIP; macOS and Linux have separate pull-request packaging workflows for dogfooding, not public release assets.

Account tokens stay in main. `AccountService.getAccessToken(resource)` accepts only the fixed sync or marketplace resource, defaults to sync, caches each audience separately and serializes persisted refresh rotations. It is not a renderer/core IPC operation or a generic authorized fetch. Saved legacy sign-ins lack marketplace authorization until an explicit browser grant upgrade. Account changes and sign-out fence responses and persistence; an unpersisted rotation cannot be reused after a cancelled sign-in. Dedicated publishing IPC binds a human action to fixed Market routes, checks its lifetime after token refresh, and strictly validates the public reply before returning it to the renderer. Preview and owner-list actions cannot authorize mutation. [The desktop publishing contract](marketplace-design.md#desktop-publishing) covers immutable retries and the production rollout limit.

Marketplace reports and human review use a separate main-frame-only typed Bridge operation. Main selects fixed routes and checks account generation and the calling document before dispatch and after awaited reads. The generic core command catalog, CLI and orglet tools cannot call it. A private main/core journal command saves up to ten unresolved public requests in SQLite before dispatch; renderer views receive no account binding or bearer token. Closing a drawer, navigating or restarting never sends a request. An explicit retry loads the original account's saved payload/key. Successful receipts clear that pending record; a later refusal cannot erase an earlier uncertain outcome. Backup/template/sync exports exclude this journal, and full data erase clears it. `pnpm test:market-moderation` exercises the real packaged shell with trusted in-process transports; it does not establish authenticated Worker HTTP behavior.

## Run

Use Windows or macOS, Node 24.19 or newer and pnpm 11.19.0.

```powershell
pnpm install --frozen-lockfile
pnpm dev
```

`pnpm dev` opens the Electron app. The Vite renderer binds `127.0.0.1`; Electron loads that loopback address even when Forge still injects `localhost`. `pnpm dev:web` only serves the renderer and intentionally has no desktop data bridge.

A new profile's Researcher has no model (owner, 2026-10-05). Its stored provider is `demo`, which now means "not connected": its empty chat lists the three ways to connect a model in place of the starters (`components/ConnectWays.tsx`), each one opening the orglet's Model field when a connection of that kind can run and Settings otherwise, a message to it opens that step instead of sending, the Model menu does not offer Demo, and the runner fails such a run with "This orglet has no model connected". An orglet that was on Demo before reads the same way; nothing switches it to a provider.

**Sample replies are a test tool.** The labelled replies that used to answer for Demo stay in the runner behind `ORGLET_DEMO_REPLIES=1` (`shared/demo-replies.ts`). `vitest.config.ts` sets it for the integration tests and `scripts/sample-replies.mjs`, which both smoke helpers import, sets it for every smoke, so both run without a key. The workspace reports it as `demoReplies`, and the window then shows Demo as it always did (`renderer/demoReplies.ts`). Where this page or another says Demo, it means a test or a smoke.

## Connect a provider

1. In **Cài đặt → Kết nối API**, turn on the provider you need. Paste the key and choose **Lưu key**, or choose **Từ tệp**. Turn the switch off to disconnect and hide the fields. Ollama has no key: turn the switch on if Ollama is running at `127.0.0.1:11434`.
2. The main process encrypts the key with Electron `safeStorage` (DPAPI on Windows, Keychain on macOS). The renderer never receives the saved key back (typed drafts are cleared after a successful save). The original `.txt`, if you used one, remains where you saved it; remove it yourself when it is no longer needed.
3. Edit Researcher, choose a connection (OpenAI, Anthropic, Grok, OpenRouter, OpenCode Zen, OpenCode Go, Ollama, a custom connection, or a local harness), then pick a model from the fetched list or type a custom ID, and save. Catalog names such as GPT-4.1 mini are suggestions only. The chat's **⋯** → **Thiết lập Tí** opens this dialog; so does **Kết nối model** under the message box of a chat on Demo (see below).
4. Select UTF-8 text files, describe the task, set a task budget and allow the selected content to be sent to the providers listed for that task.
5. Send the task. Open **Chi tiết** for activity or source references. Accepting a report only updates its status in Orglet.

**From Demo to a real model (COD-293).** While any orglet of a chat is on Demo, the line under its message box (the empty chat's and the open chat's alike, `DemoNote`) carries **Kết nối model**, and the Demo answer names that button instead of "a local harness". It sets up the chat's orglet (a lead channel's lead first, `demoWorkerToConnect`). When a connection other than Demo can already run (a saved key, a signed-in harness, a custom connection; `connectModelStep` over the Model menu), the orglet's dialog opens on the Model field with that connection chosen, as a new orglet starts, and **Lưu Tí** switches it. When only Demo can run, Settings opens on **Kết nối API**; closing Settings refreshes the workspace and, if a connection can run now, opens that dialog the same way, and nothing otherwise. The chat header names the provider of whoever answers the next message, read from the orglets as saved, so it changes on save rather than after the next turn; each earlier answer keeps its own provider in its byline. The header's **⋯** leads with **Thiết lập Tí** (a chat with one orglet, side threads included) or **Thiết lập hội** (a crew's chat), then **Thiết lập chat** for the chat's name, assignees and limit (`chatSettingsTarget` in `renderer/chatSettings.ts`); a group chat has only the latter. The pattern follows comparable local AI apps: the chat itself carries the step that leads to setup (LM Studio's model loader, Msty's first-run buttons), the provider is added in Settings and the model picked afterwards where the conversation is (Jan), and a sensible model is preselected (Msty, Jan).

The worker dialog lists each connection and, for every non-Demo worker, a model ID field: pick from that provider's cached list or type a custom ID. Catalog IDs in `apps/desktop/src/core/adapters/catalog.ts` (`gpt-4.1-mini-2025-04-14`, `claude-sonnet-5-5`, `grok-3-mini`, `openai/gpt-4.1-mini`) and the Ollama suggestion `llama3.2` are suggestions, not a lock. Core fetches each provider's own model list (`modelList`), caches it for 24 hours in SQLite `settings.modelLists`, and always accepts a typed custom ID if the fetch fails. Leaving the ID blank keeps the catalog suggestion (or the CLI default for a harness). A connection with nothing to fall back on (a custom connection, OpenCode Zen or Go) marks the field required and, once its list is fetched, fills an empty field with the first model it can call, and Ollama does so when `llama3.2` is not installed (`startingModelId` in `renderer/components/workerModel.ts`, COD-293). The fill happens once per connection while the dialog is open, so an ID the person clears stays cleared; a list that failed or came back empty does not count. If the cached list marks that selected or suggested ID as deprecated, the picker shows a quiet chip; the sunset date is included only when the native payload had `shutdown_date`. A saved key does not establish that the provider account has credits. No subscription credentials are imported. See [model-list-fetch.md](model-list-fetch.md).

### Custom OpenAI-compatible connections (COD-242)

**Kết nối tùy chỉnh** in **Cài đặt → Kết nối API** adds any server that speaks the OpenAI chat/completions API: a name, a base URL and an optional key, up to 16 of them. User steps: [connections.md](connections.md#custom-connections).

- **Data model.** Each connection is `{ id, name, baseUrl, price? }` (`shared/custom-connections.ts`), stored in SQLite `settings.customConnections` and sent to the window in `Workspace.customConnections`. Its provider id is `custom:<id>`, a member of `ProviderId` beside the built-in ones, so an orglet stores it in `provider` like any other and the budget ledger, `ProviderSlots`, task consent (`providerScopes`) and the model-list cache (`settings.modelLists.byProvider`) keep one entry per connection. Names are unique, case-insensitively. `saveCustomConnection` and `deleteCustomConnection` are core commands; delete is refused while a live orglet uses the connection.
- **The key.** Main keeps it with `safeStorage` in `custom-<id>.credential` beside the built-in key files (`main/credentials.ts`); any visible ASCII token without spaces, up to 500 characters, is accepted. `connect('custom:<id>', key)` only stores a key for a connection the core still has, and after `deleteCustomConnection` main removes the file. The renderer learns only `Connections.custom[id] === true`. Without a key the adapter sends no `Authorization` header (the OpenAI SDK's `Authorization: null`).
- **Base URL rule.** `checkBaseUrl` accepts `http:` or `https:` only, with no user name, password, query or fragment, and strips a trailing slash. Plain `http:` is allowed only for loopback, private IPv4 (10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10), IPv6 `::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped private addresses, `localhost`, `*.localhost` and `*.local`; any other host is refused, not warned about. The form checks as you type and the core checks again on save.
- **Requests.** `CustomConnectionAdapter` wraps `OpenAIAdapter` with the saved base URL and model; there is no default model, so saving an orglet needs a model ID. Failures name the connection: a refused key (401/403), an unknown model (404), too many requests (429), a server that is not running.
- **Cost.** `isPaidApi` is true for a custom connection, and `connectionPricing` decides its price. An entered price (`price: { inputMicrosPerMillion, outputMicrosPerMillion }`, integer USD micros per million tokens, both or neither, up to $1,000) always wins. Without one, a base URL on a local or private address (the plain-http list) is priced at zero, and any other host has no rates. With rates, `resolveWorkerModel` returns them (`pricingVersion` `entered:` or `local:<model>:<in>:<out>`) and the request is reserved and settled by `cost()` from the reported tokens, like a built-in paid API. A zero price goes through `BudgetLedger.reserveAtZeroPrice`, a zero hold that never waits for budget, because `reserve` still refuses a zero amount as a missing price. Without rates, the request holds the rest of the task budget and becomes an unknown charge in **Khoản cần đối soát**. A reply with no token counts is marked unknown at every price, so it stays visible; on a free connection it holds zero. A failed or stopped request is marked unknown too, except at a known price of zero, where it is settled at $0 with no tokens: nothing can be owed, so it never becomes a charge to reconcile (COD-295). The monthly per-connection cap applies to each connection on its own. The price is part of a routine's approval fingerprint, so changing it asks for approval again.
- **Model list.** `GET {baseUrl}/models` with the key when there is one, parsed like OpenAI's list (the same display filter hides embedding and speech IDs), cached 24 hours; saving a new address or deleting the connection drops its row.
- **Backup and erase.** Backups carry `customConnections` (names and addresses, never keys); restore adds missing ones by id and renames one whose name is taken. A full erase keeps the list, as it keeps the key files.

### Live acceptance (manual)

One authorized OpenAI or xAI task may be run against the real API with a **$0.05** budget. Orglet never searches for keys.

```powershell
$env:ORGLET_LIVE_KEY_FILE = 'C:\path\to\key.txt'
$env:ORGLET_LIVE_PROVIDER = 'openai'   # or 'xai'
pnpm test:live
```

Anthropic live acceptance needs a separate authorization and is not covered by `pnpm test:live`.

## Thinking effort

An orglet's **Thinking effort** setting is optional: Automatic, Low, Medium, High or Maximum. Automatic requests medium for all scheduled work, members and other chat turns. A channel lead's plan and synthesis use high outside schedules. An explicit choice takes precedence. Maximum means the highest named level evidenced for the selected model and transport. It does not change the output token cap, budget, timeouts or permissions.

New runs first refresh pre-effort native metadata; a newly selected Ollama model is inspected even when its tags cache is fresh. Cache version 3 migrates version 2 rows without discarding verified prices. A failed metadata refresh stays unverified. Frozen and legacy resumes skip this preparation.

Before its first dispatch, each run freezes the requested effort, its explicit or contextual origin, support status and, when supported, the native setting. A harness's resolved model ID is frozen at the same point; saved model aliases remain the person's choice for future runs. Resuming uses that snapshot after model lists or orglet settings change. A legacy run with a checkpoint or earlier request, but no effort snapshot, stays unverified and sends no new effort parameter. Its existing Anthropic prefix digest is preserved; effort-enabled requests bind the new configuration into that digest.

The dialog and activity trace say when support is unverified or the selected level is unsupported. The field is then omitted and the connection keeps its default; Orglet does not select a different model. Current support follows the actual request route:

- OpenAI and xAI use documented named levels for exact model IDs on Chat Completions with tools. GPT-6 Astra and GPT-6.1 Sol are unsupported on this route because their Chat Completions endpoint does not support function calling; [OpenAI's reasoning guide](https://developers.openai.com/api/docs/guides/reasoning) directs that use to Responses. This does not describe native Codex support.
- Anthropic's documented models use `output_config.effort` with adaptive thinking on supported models. Adaptive requests use automatic tool choice and parallel tool use off. Signed thinking replay is bound to that configuration as well as the prompt, tools and message prefix. A no-tool answer gets one bounded correction. [Anthropic effort](https://platform.claude.com/docs/en/build-with-claude/effort).
- Codex preserves `supportedReasoningEfforts` from its native model list and uses `model_reasoning_effort`. Claude Code uses `--effort` for exact supported model IDs. Gemini's exact supported models get a generation override in the private run's settings file; the lockdown remains in place. Cursor exposes no evidenced effort control here.
- OpenRouter preserves the model's `reasoning.supported_efforts`; a null list accepts all gateway levels, an omitted list is unverified. Dynamic auto/free routers stay unverified. [OpenRouter reasoning options](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens#discovering-per-model-reasoning-options).
- Ollama reads `thinking.values` from `/api/show` only for locally selected models. Named values are preserved; boolean on/off controls do not establish effort levels. An unavailable metadata request leaves support unverified. [Ollama thinking controls](https://github.com/ollama/ollama/blob/main/docs/capabilities/thinking.mdx).
- OpenCode and custom connections remain unverified. No provider-wide maximum or speculative token budget is sent.

The optional orglet preference travels through revisions, backups and templates. App proposals use `effort: "auto"` to clear an override; null leaves it unchanged. A marketplace update preserves an installed orglet's local choice, including a deliberate absence. Run snapshots keep the setting they started with.

## Local harnesses (Claude Code, Codex, Cursor Agent, Gemini CLI)

Orglet can also run a worker through an agent CLI already installed on the machine, signed in as that CLI itself or as one of the accounts added in Settings (see [Accounts](#accounts) below). **Cài đặt → Harness trên máy** always lists Claude Code, Codex, Cursor and Gemini CLI. Each row is **chưa cài** (not installed), **đã thấy · chưa đăng nhập** (found on disk), **đã đăng nhập · sẵn sàng** (signed in, ready to run) or **lỗi đăng nhập** (the status probe failed). Found on disk is not ready. A failed harness login does not fall back to Demo. **Dò lại** probes again after installing or logging in. Detection runs only each CLI's `--version` and its own login-status command (Gemini CLI has none; see its entry), and looks in:

Account addresses a CLI or its plan reading reports (such as the Claude Code or Codex sign-in) are shown only in part on screen, `an•••@example.com`, through `shared/pii.ts`; so is the CodePawl account's email. The full address is never needed to tell accounts apart, and a screenshot or a screen share then does not carry it.

- Claude Code: `PATH`, `~/.local/bin`, npm/bun/volta global bins, `~/.claude/local`, and the build Claude desktop downloads (the Claude MSIX package's `LocalCache\Roaming\Claude\claude-code\<version>`, then `%APPDATA%\Claude\claude-code\<version>` on Windows, or `~/Library/Application Support/Claude/claude-code/<version>` on macOS). The package folder comes first because `%APPDATA%\Claude` is only a view processes inside the Claude package see. Sign in with `claude auth login`. The settings row copies a path: your own install (PATH, npm) when one answers `--version`, because the desktop app's build moves to a new version folder on every update, and the app's build only when nothing else is installed. Runs still prefer the app's build, which starts without a shell. The Codex desktop app's content-hashed build is treated the same way. The desktop app's session is not reused.
- Codex: `PATH`, npm global bins and the Codex desktop app's `%LOCALAPPDATA%\OpenAI\Codex\bin` (Windows) or `/Applications/Codex.app/Contents/Resources/codex` (macOS). Sign in with `codex login`. An expired ChatGPT token can still look signed in until a run fails; then sign in again. Orglet does not call a paid model just to check this.
- Cursor Agent: `PATH`, `~/.local/bin`, `%USERPROFILE%\.cursor\bin\agent.exe` (install script), and `%LOCALAPPDATA%\cursor-agent` (`agent` / `cursor-agent`). Sign in with `agent login`; install with the documented `curl https://cursor.com/install -fsS | bash` or Windows `irm 'https://cursor.com/install?win32=true' | iex`.
- Gemini CLI: `PATH`, the npm/bun/volta global bins (`npm install -g @google/gemini-cli` puts `gemini.cmd` in `%APPDATA%\npm`), `~/.local/bin`, and on macOS Homebrew's `/opt/homebrew/bin` and `/usr/local/bin`, because an app opened from the Finder does not get the shell's `PATH`. It is an npm package, so on Windows it is always a `.cmd` shim started through `cmd.exe`; its arguments are short and the prompt goes on stdin. It has no login subcommand and no status command. Sign in by running `gemini` bare and choosing **Sign in with Google** (the row says so). Detection reads the CLI's own folder, `<GEMINI_CLI_HOME or home>/.gemini`: the method in `settings.json` (`security.auth.selectedType`, found by its key because the file allows comments) or the environment variables the CLI falls back to (`GEMINI_API_KEY`, `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_GENAI_USE_GCA`, `GOOGLE_GEMINI_BASE_URL`), then for a Google sign-in whether `oauth_creds.json` holds a token, and the address in `google_accounts.json`. A file it cannot read makes the row **lỗi đăng nhập**. With `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE=true` the sign-in sits in the system keychain, which Orglet does not read; the row then trusts the chosen method, and a missing sign-in fails the first run with the Settings hint.

While a run works, a tab docks onto the top of the prompt bar, its lower corners curving into the bar so the two read as one surface. It carries the faces of the workers actually running, a sentence naming who is doing what ("Researcher is thinking…", or how many are working in a team; a long name shortens before the action does), and above it one grey line for the last step that finished. The faces carry the state in the same motions as the byline — turning while thinking, eyes sweeping a line while reading, following the line while writing — rather than a coloured mark to learn. The tab rises out of the bar when a run starts and, when it ends, its content fades first and the shape is drawn flat back into the bar. It says only what the core observed. Claude Code streams its steps (`apps/desktop/src/core/harness/claudeStream.ts`), so reads and searches are named; Codex streams reasoning and the answer only, and an API provider reports nothing finer than planning, combining and waiting, so those runs get an island with fewer states and no receipt line. The step list, the elapsed time and the worker's notes sit behind one folded control above the streaming text, the same trace the finished answer keeps above its text (COD-220: the memories used, the notes loaded and every step the core saw, in order), so nothing sits under text that already reads as complete (COD-212); the control counts what happened ("Used 1 memory · Read 2 files"), or says **Chi tiết** when only notes are there to open, and a run with neither shows the elapsed time as one plain line instead. With `prefers-reduced-motion` every change is a cut and the tab simply appears and disappears. The words the island and the step line use for each kind of action, what is kept after a run, and the diff of what a run changed in its working copy (the **Đã thay đổi 3 tệp · +42 −7** line under the answer, read through the `workspaceDiff` command) are decided in [worker-actions.md](worker-actions.md). Once no run is on, the same tab offers the chat's knowledge suggestions waiting for review (a lightbulb, "3 knowledge suggestions", **Review** and a dismiss): Review opens the one note, or **Thư viện → Knowledge** when there are several, and dismiss only hides the offer for that set of suggestions, so a new suggestion brings it back and the notes stay in the library either way. A working run always takes the tab first; the offer returns when the run ends.

Source-only Codex runs keep the strict `{ payload: string }` CLI envelope. The prompt includes the canonical inner answer schema generated from the frozen run and its allowed proposals, memories and reactions, so a requested report has the same fields and enums the core accepts. Decoding still passes through the existing answer and report validators, citation checks and hand-in gates. This guidance grants no tools or permissions; channel runs retain their tool-loop protocol.

### Accounts

A harness row runs with one account, picked on the row itself. **Tài khoản mặc định** is the sign-in the CLI already has on this machine — what Orglet used before accounts existed, and what a fresh install shows.

The row menu adds, renames and removes accounts. An account is a folder: Orglet creates one under `<userData>/harness-accounts/<harness>/<id>` and points the CLI at it with the variable that CLI reads for its own config and credentials — `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `CURSOR_CONFIG_DIR` or `GEMINI_CLI_HOME` (Gemini CLI makes its `.gemini` folder inside it). Cursor Agent also gets the variable its sign-in follows, set to the same folder (`harnessAccountVariables` in `shared/harness.ts`, see below). Signing in is still the CLI's job: the login command the row copies sets those variables first, so the sign-in lands in the selected account. Gemini CLI's line is the program alone (`$env:GEMINI_CLI_HOME = "…"; & "…\gemini.cmd"`), since it signs in from its own menu. On Windows the row writes that line for PowerShell (`$env:VAR = "…"; & "…" auth login`), Command Prompt (`set "VAR=…" && "…" auth login`) or Git Bash (`VAR='…' '/c/…' auth login`), picked beside the command and remembered; macOS and Linux get one POSIX line. `tests/integration/login-commands.test.ts` runs every Windows form in its real shell (COD-230). The status, version and login command above the picker all describe the selected account, and every run of that harness uses it.

**Sign in and sign out from the row (COD-327).** A Claude Code, Codex or Cursor Agent row that is not signed in has a **Đăng nhập** button above the login command, which stays as the fallback (**Hoặc chạy lệnh này trong terminal**). It signs in the selected account without a terminal, in that account's folder, through the CLI's own flow (`apps/desktop/src/core/harness/sign-in.ts`):

- **Codex:** `codex app-server` in the account's `CODEX_HOME`, sent `initialize`, then `account/login/start` with `{ type: "chatgpt" }`. It answers a `loginId` and an `authUrl`; the core hands the address to main, which opens it with `shell.openExternal` only when it is an `https` page on `auth.openai.com`, `chatgpt.com` or another `openai.com` host (`signInPageAllowed` in `shared/harness.ts`). The app server listens for the browser's return itself and stays up until `account/login/completed` names that `loginId`; **Hủy** sends `account/login/cancel`. Checked against codex-cli 0.157.0's generated protocol and a start-then-cancel on an empty `CODEX_HOME` on 2026-09-29.
- **Claude Code:** `claude auth login` with no terminal. Claude Code 2.1.283 prints the manual address, listens on `127.0.0.1` for the browser's return, and opens the browser itself (or the program in `BROWSER`); it exits 0 with `Login successful.` Stdin stays open and empty; Orglet does not offer the paste-a-code path.
- **Cursor Agent:** `agent login`, which opens the browser itself (unless `NO_OPEN_BROWSER` is set) and polls until the page reports back, then exits 0. On Windows its launcher is `cmd.exe` → PowerShell → node, so **Hủy** stops the whole tree with `taskkill /T`.
- **Gemini CLI** signs in from its own menu and keeps only the copied command.

While it waits, the row shows one line, **Đang chờ bạn đăng nhập trong trình duyệt…**, and **Hủy**, with no spinner. The wait can take minutes, longer than a command may, so `startHarnessSignIn` returns at once and the ending arrives as a change notice; the Settings window then reads the rows again. Whatever the ending, the core does not trust the CLI's word: it detects that harness again and reads plan usage afresh. A failure keeps the CLI's last line (without any address) under the button until the next try. After ten minutes the core stops the sign-in. One sign-in runs per harness, for the account that was selected when it started: picking, adding or removing an account cancels it, and quitting Orglet stops it.

**Đăng xuất** in the account menu runs the CLI's own sign-out in the selected account's folder, after a question in the menu: `claude auth logout`, `codex logout` or `agent logout`. Gemini CLI has only `/logout` inside its own window, so its row offers none. For the default account the question says it signs that CLI out on the whole computer, not only in Orglet; so does every Cursor Agent sign-out on macOS, where its accounts share the Keychain sign-in (below). An added account's sign-out runs with the same variables as its runs, so on Windows and Linux `agent logout` clears only that account's `auth.json`. The renderer never sees a token: it sends the harness and the account id, and only the core starts the CLI.

Orglet never copies, stores or writes the credentials in those folders; it reads the access tokens of Claude Code, Cursor Agent and Gemini CLI only for plan usage below. Removing an account deletes its folder, and with it that sign-in; the default account takes over. On macOS, Claude Code may keep credentials in the Keychain rather than in its config folder, so separate accounts are only verified on Windows. Gemini CLI keeps one keychain entry for every folder when `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE` is set, so with that variable only its default account is meaningful.

**Cursor Agent accounts (COD-330).** Cursor Agent 2026.09.18 keeps its sign-in outside `CURSOR_CONFIG_DIR`, which moves only `cli-config.json`. Its bundled `cli-credentials` module picks the store (`AGENT_CLI_CREDENTIAL_STORE`: `file`, `memory`, or by default the Keychain on macOS and a file elsewhere), and `getAuthFilePath` builds the file's path from `APPDATA` on Windows (`%APPDATA%\Cursor\auth.json`) and `XDG_CONFIG_HOME` on Linux (`$XDG_CONFIG_HOME/cursor/auth.json`, `~/.config` when unset). Its public docs name no variable for this: only `CURSOR_API_KEY`, and `CURSOR_CONFIG_DIR` / `XDG_CONFIG_HOME` for the config file. So an added account sets `APPDATA` (Windows) or `XDG_CONFIG_HOME` (Linux) to its own folder next to `CURSOR_CONFIG_DIR`, and signs in to `<folder>\Cursor\auth.json`. Every run, detection probe, `agent about` for plan usage, the token read for plan usage, **Đăng nhập** and **Đăng xuất** use those same variables, so each account signs in, runs and reads usage as itself. On 2026-09-29 `agent status --format json` against the installed 2026.09.18 build ignored a dummy `auth.json` in an account folder with only `CURSOR_CONFIG_DIR` set, and read it once `APPDATA` pointed there too. The CLI reads `APPDATA` in one other place, the Cursor editor's `workspaceStorage` for an opened folder (`vscode-repo-key-provider`), which Orglet's private run folders never have. Programs the CLI starts inherit the variable, but Orglet runs it in ask mode with its sandbox, and most Windows programs look their folders up through the system rather than the variable; tools that read `%APPDATA%` directly (npm's global folder, for one) would see the account folder while the CLI runs. The copied login line puts `APPDATA` back after the CLI exits in PowerShell (`[Environment]::GetFolderPath('ApplicationData')`) and Command Prompt (`%APPDATA%` is expanded before the line's first `set`); Git Bash and POSIX shells set it for the one program only. On Linux the browser `agent login` opens inherits `XDG_CONFIG_HOME` too; a browser that is already open is unaffected. `CURSOR_AUTH_TOKEN` is no way out: the CLI writes a token it is given into the same store. On macOS the sign-in is the Keychain item `cursor-access-token` for the whole computer, and moving it to a file would only move it to `~/.cursor/auth.json`, still one per computer, so there Settings offers no **Thêm tài khoản** for Cursor Agent and says why behind the row's "i", and the core refuses to add one (`harnessAccountsSignInApart`). Separate Cursor Agent sign-ins are checked against the CLI's code and the dummy-file run above; two real Cursor accounts have not been signed in side by side, and Linux has not been run.

### Plan usage

Under each signed-in row, Settings shows who the selected account is (address and plan) and how much of each plan allowance it has used, with when that allowance resets. The account picker shows the same for every account, as the address and the percentage of the allowance closest to its limit, so a switch can go to the account that still has room. The core reads this through the `harnessUsage` command, apart from detection because it goes over the network: every account of every installed harness, the default account first, one account at a time, reused for a minute, and read again on **Dò lại** or after an account changes (`apps/desktop/src/core/harness/usage.ts`).

- **Claude Code:** `claude auth status` for the address and plan, then the access token in that account's `.credentials.json` (for the system account: the folder in `CLAUDE_CONFIG_DIR` when Orglet runs with it, else `~/.claude`, as Claude Code itself does, COD-339) goes to `https://api.anthropic.com/api/oauth/usage`, the endpoint Claude Code's own `/usage` reads. The token stays in the core and is sent nowhere else. Claude Code renews its access token only when it runs (`claude auth status` does not, and there is no read-only refresh command), and Orglet never renews it or writes Claude Code's credentials: a rotated refresh token would sign Claude Code itself out. So between runs the saved token is often expired while the person is signed in and working. Such a read does not call the endpoint and is not shown as a sign-in problem (COD-301): the row shows the last good reading of that account with its time (**Số liệu lúc 07:05**) and says Claude Code renews the sign-in the next time it runs. Those readings live in the settings table as `harnessUsageReadings`, one per account: address, plan, windows and time, never a token. A window whose reset has passed is left out, and a reading is forgotten when the account signs out, shows another address or is removed. When an Orglet run on Claude Code ends and the usage on hand had that account expired, the core reads usage again at once, since the run renewed the token (`core/harness/usage-readings.ts`). A failed read shows the last reading the same way. Such a row is never offered as an account with room. An API-key sign-in has no plan allowance. On macOS, where `.credentials.json` holds no token, the sign-in comes from Claude Code's Keychain item through `/usr/bin/security find-generic-password -s <service> -w`: the service is `Claude Code-credentials`, and for an account folder `Claude Code-credentials-<first 8 hex digits of the SHA-256 of the NFC-normalized CLAUDE_CONFIG_DIR>`, the rule Claude Code 2.1.283 uses. That read is unit-tested with an injected Keychain; it has not been run on a Mac, and macOS may ask once before `security` reads another app's item.
- **Claude banked resets (COD-328):** the usage request carries `?cedar_ember=1`, which adds Claude's banked-reset block to the same answer: `cedar_ember: { eligible, next_grant_id, grants: [{ id, resets_left, ends_at, paused, usable_now }] }`. Settings counts the resets of every grant that is usable now, not paused and not past `ends_at`, and shows them under the bars only when there is at least one, with when the next one ends (**Còn 2 lượt reset · lượt tới hết hạn 22/10**). The grant id stays in the core. **Dùng một lượt reset** asks first, naming the account and saying that Claude resets the current five-hour session allowance, that the weekly one stays, and that it uses one of N. Only then does the core send `claimHarnessReset`: it reads usage again for the grant Claude names next, then posts `{ program: 'cedar_ember', grant_id, request_id }` to `https://api.anthropic.com/api/organizations/<organizationUuid>/reset_rate_limits` with the account's own token. The organization comes from `oauthAccount.organizationUuid` in Claude Code's `.claude.json` (in the account folder, or the home folder for the default account). Claude answers `reset`, `not_limited`, `already_used`, `ineligible`, `cooldown` or `unavailable`. Only `reset` is a success toast; the others say that nothing was spent. A refused token, 429, a cooldown or a malformed request is an error saying no reset was used. `unavailable`, a server error or no answer at all is an error saying Claude could not confirm it, and the next try sends the same `request_id`, which Claude treats as the same claim. A second click while a claim runs joins it. Usage is read again after every attempt. Nothing spends a reset on its own. With an expired saved sign-in the row keeps the last count from the stored reading, offers no action; the line under the bars already says Claude Code renews the sign-in when it next runs. The block and the claim follow Claude Code's own protocol; no claim has been sent from Orglet against a real account, and what a reset clears (the session allowance only) comes from Claude Code's public behaviour, not from a measured answer. `tests/integration/claude-banked-resets.test.ts` covers the shapes with a fake fetch.
- **Codex:** `codex app-server` in that account's `CODEX_HOME`, asked `account/read` and `account/rateLimits/read`. Only the plan's own `codex` limit is shown; a model-specific one is not. Which windows an account has is the service's answer: Codex passes its `primary_window` and `secondary_window` through with their length (`windowDurationMins`), and Orglet names each by that length, not by its position. A ChatGPT Pro 5x account answered with one week-long window and no five-hour one on 2026-09-27 (codex-cli 0.157.0); a plan that has both shows both.
- **Cursor Agent:** `agent about --format json` for the address and plan tier, then the call Cursor Agent's own `/usage` makes: `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentPeriodUsage` (Connect, JSON, body `{}`) with its access token as the bearer. The token comes from where the CLI keeps it for that account: `CURSOR_AUTH_TOKEN` if set, else the account's `auth.json` (`accessToken`, see Cursor Agent accounts above) or, on macOS, the Keychain item `cursor-access-token` unless `AGENT_CLI_CREDENTIAL_STORE=file`. It is a JWT; one whose `exp` has passed is not sent and reads as expired, like Claude Code's, until the CLI renews it on its next run. The answer's `planUsage` gives three rows, named as the CLI names them: the included usage (`totalPercentUsed`, or `includedSpend / limit`), then the `Auto` and `API` pools, each resetting at `billingCycleEnd` (milliseconds) and called a month when the cycle is. A team or enterprise plan answers without `planUsage` and shows no bars, as in the CLI. `CURSOR_API_KEY` or an `auth.json` holding only an API key has no plan allowance. The field names and the percent rules are from Cursor Agent 2026.09.18's bundle; no signed-in answer has been read live yet.
- **Gemini CLI:** the address from `google_accounts.json`, then, for a Google sign-in, the calls its `/stats` and `/model` quota views make on the Code Assist API: `POST https://cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` for the project (`cloudaicompanionProject`, or `GOOGLE_CLOUD_PROJECT`) and the plan name (`paidTier` or `currentTier`), then `v1internal:retrieveUserQuota` with that project. Each bucket is one model's allowance: used is `1 - remainingFraction`, with its `resetTime`; the docs give the quota per day, so the row reads **Ngày · gemini-2.5-pro**. The token is `access_token` in `oauth_creds.json`. Google's access tokens last an hour and Gemini CLI renews it when it runs, so outside that hour the read is expired and shows the last reading, as for Claude Code; Orglet never renews it, and an Orglet run on Gemini CLI triggers the fresh read. An account the CLI has not set up (no `currentTier`) is left alone, since setting it up (`onboardUser`) is a write. An API key, Vertex AI, or a sign-in in the system keychain (`GEMINI_FORCE_ENCRYPTED_FILE_STORAGE`) shows no usage. Read from google-gemini/gemini-cli (`code_assist/server.ts`, `setup.ts`, `types.ts`, `config.ts`, `ModelQuotaDisplay.tsx`) on 2026-09-29; not yet run against a live account.

After an Orglet run on Claude Code, Cursor Agent or Gemini CLI, usage is read again when the usage on hand had that account expired, since the run renewed its token.

**OpenCode Go** is an API connection, not a harness, so its usage sits under its row in **Cài đặt → Kết nối API** once a Go key is saved: the five-hour, weekly and monthly allowances from `GET https://opencode.ai/zen/go/v1/usage` with the key as the bearer (the `openCodeGoUsage` command, `core/adapters/opencode.ts`). The answer is `usage.rolling`, `usage.weekly` and `usage.monthly`, each a `percent` and a `resetsAt`, as served by the opencode console (`packages/console/app/src/routes/zen/go/v1/usage.ts`, read 2026-09-29). A `403` means the key has no Go subscription and the row says so. The core asks main for the key for that request only and returns no key; the answer is reused for a minute and read again when a key is saved or replaced. OpenCode Zen has no such endpoint.

When a turn stops because the harness account ran out of plan usage, the runner marks the run `plan_limit` (from the CLI's own refusal, `HarnessLimitError`; a rate limit is not marked, since it passes in minutes). Only a refusal of the plan itself counts (COD-301): Claude Code's `rate_limit_event` with `status: rejected` on a plan window (five-hour, weekly, or its extra usage) while no extra usage carries the requests on, or the CLI's own plan words ("You've hit your session limit", Codex's "You’ve hit your usage limit", out of credits, a spend cap). A limit on one model (Claude's weekly Opus or Sonnet allowance, Codex's "usage limit for <model>. Switch to another model") says to pick another model and is not marked, since the account still runs the others. Server throttling (Claude Code's "not your usage limit"), overload, a dropped connection, Codex's spent retries and sign-in errors are not limits of the plan either. Codex prints a retry it went on from ("Reconnecting... 2/5") as an `error` line, so only `turn.failed` ends a Codex run. The reset time is the provider's: Claude Code's `resetsAt`, or the time Codex writes into its message ("try again at 9:15 AM", or "Oct 4th, 2026 9:15 AM" for another day). The shapes are in `tests/integration/harness-limit-shapes.test.ts`, taken from Claude Code 2.1.280 and codex-cli 0.157.0. Once no run is on, the island on the prompt bar offers the switch in that chat: **Codex hết hạn mức · Dùng Work · còn 70%**. The account offered is the other one with the most room, from a fresh usage read; one that is signed out, expired, unread or full is never offered. The action selects that account and runs the turn again. With no other account that has room, the island says when the one in use resets instead. The offer lasts while an orglet's latest run in the turn is the one that ran out; once it runs again, whatever the result, the offer goes (COD-226). It takes the island before the knowledge-review offer, and dismissing hides it for that run only (`shared/account-switch.ts`, COD-225). Before any run stopped on it, a plan the usage read shows as out takes the same island in place of the line under the bar, whenever the thread docks nothing else, in a chat and in an empty one (`usePlanUsageBar`, the `fallback` of `IslandDock`); its switch only selects the account, since nothing was sent, and × hides it until that account's reset changes.

The same numbers sit under the message box (COD-326): a ring at the far right of the toolbar row under the box, after the model or recipient control (`UsageRing`, passed to `Composer` as `usage`). The box itself holds only the text, its attachments and reply zones, and the send or stop button, a 30px circle at its bottom right on the last text line: send is a muted arrow with no fill until there is text to send, then fills with the accent; during a run stop takes the slot, and typing brings send back beside it; the toolbar row carries the **+** at its left and the model picker, recipient list or side-thread send options at its right, 28px controls on one centred line whose sides match the box's inner padding. The note line (what to do first, the plan line, the permission hint, the read-only line) is its own centred row under the toolbar (`ComposerFoot`), so a sentence with a button never squeezes the controls. It shows the share of whichever is closer to its limit, the tightest plan allowance of the account in use or the model's context window (`usageRingFor` in `shared/composer-usage.ts`), muted under 80%, `--warning` from 80%, `--error` at 100%. A click opens an `AnchoredPopover` with the context window, each harness's plan in `PlanUsage` rows with the account and, for an earlier reading, **Số liệu lúc 07:05**, and **Xem chi tiết** to Settings → Harness. Which harnesses count is `composerUsageFor`: API providers, Demo, and accounts with no windows (signed out, an API-key sign-in, Cursor Agent, Gemini CLI, an expired sign-in with no stored reading) give nothing. In a crew or group chat the harness closest to its limit is shown, since it stops the chat first; a tie keeps roster order, and the details list the others after it. From 80% of a plan allowance the note line says how much is used and when that allowance resets; at 100% it says when the account has room again (the latest reset among the full windows) and offers the account `accountSwitchFor` picks, the one the island would offer; clicking it runs `selectHarnessAccount` and nothing else. The out line waits while the island already shows its own account offer and comes before the permission hint (COD-305); the 80% line gives way to that hint. The renderer keeps one copy of the `harnessUsage` answer for the window (`renderer/planUsage.ts`): it asks when a chat opens and when an account changes (both reuse the core's one-minute copy), reads again (`refresh: true`) when a run in the open chat ends and a few seconds after the shown allowance resets, and asks every five minutes while the window is visible. Nothing is read for a chat with no harness.

The popover opens with the context window of the model each orglet of the chat will use next: its saved model or, with none saved, the one its CLI or connection names as its default (`chatContextFor` in `shared/composer-usage.ts`). One orglet gets one row, the model beside the title; a channel gets a row per orglet in roster order, and the ring follows the fullest row whose window is known. Demo gets no row, and an empty chat gets the same rows with nothing used. A row reads "used / window (percent)" over a 4px bar on the ring's scale (muted, `--warning` from 80%, `--error` at 100%); the plan rows under it use the same row, with the reset and the percentage at the right. Used is what that orglet's latest run in the chat sent on its last request, 0 before its first run there. The window is, in order: what a run in the chat reported for the same model (every name of the default, unset, its alias or the id the CLI resolved it to, counts as the default), then the model list's `contextTokens`. The list's figure is the provider's own (OpenRouter's `context_length`, or the Models API's `max_input_tokens` for Anthropic and for Claude Code, whose list reads the Models API with the account's sign-in and gives each alias the window of the model it resolves to) or the window a harness reported for that model on an earlier run in any chat: when a harness result carries a window, the runner keeps it in the local setting `reportedContextWindows` (connection, then model id, then tokens; up to 100 models per connection; never in a backup), counting a run on the CLI's default for the list's `isDefault` model (`rememberReportedContextWindow` in `core/models/cache.ts`), and `modelList` adds it to every entry without a window of its own (`withReportedContextWindows`). The renderer reads that connection's list again once after such a run. With neither, the row says the size is unknown and draws no bar; no window is ever taken from a table in the code. No harness reports an auto-compact threshold, so the popover shows none, and Orglet has no compact action. Each run's `contextUse` (`usedTokens`, `windowTokens`) is set by the runner from what the provider reported for the run's last model request. Claude Code: its `result` line's `usage.iterations`, whose last entry is the last request (input plus cache creation plus cache read), and `modelUsage[model].contextWindow`, the window Claude Code runs that model with (`core/harness/context-use.ts`; measured on Claude Code 2.1.283: one call sent 33,436 tokens against 1,000,000). Without `iterations` nothing is recorded, since the top-level `usage` adds every request together. Codex: `codex exec --json` reports only the turn's summed `usage` on `turn.completed` and no window, so nothing is recorded. API connections: the prompt tokens the provider billed for the latest request, and the window only where the model list gives one (OpenRouter's `context_length` or Anthropic's `max_input_tokens`, kept as `contextTokens`); elsewhere the window is unknown and the row says so. Orglet trims a chat by turns, not by the window (`core/context/thread.ts`): each message sends up to the last 10 turns word for word, at most 24,000 characters of them, and older turns are folded into an extractive summary. The popover does not explain this; it shows the figures only, and this page and the chat guide carry the explanation.

Every percentage is the vendor's own number; nothing is estimated. Detection reads Cursor Agent's `status --format json` through its `isAuthenticated` field.

Pick **Claude Code trên máy này**, **Codex trên máy này**, **Cursor Agent trên máy này** or **Gemini CLI trên máy này** as a worker's connection, then optionally a model ID (`--model` / Codex and Gemini CLI `-m`). Empty ID keeps the CLI default. Each task still needs explicit consent for that harness. Core lists models for those CLIs (`codex app-server` `model/list`, `agent --list-models`, Claude Code aliases named by the model the CLI starts with, Gemini CLI aliases), marks the one each CLI runs by default, and always accepts a typed custom ID ([model-list-fetch.md](model-list-fetch.md#versions-and-the-default-cod-332)). A standalone source-only run copies the permitted, hash-checked sources and the skill's reference files into a temporary folder, sends the compiled context as the prompt and requires the same JSON report schema; Orglet then applies the same citation, checker, checklist and line-range checks as native runs and deletes the folder.

The following settings describe that source-only path. Workspace, team, web and dataset-tool runs use the core tool loop described below. A source-only answer can still propose app changes: they travel as an `appProposals` array in the answer instead of tool calls (see [agent tools](agent-tools.md#proposing-app-changes)).

- Claude Code runs with `-p --restricted --safe-mode --strict-mcp-config --tools Read,Grep,Glob --no-session-persistence`, so it has no command, web or MCP tools, ignores your hooks, plugins and CLAUDE.md, and its file tools stay inside the task folder. A PDF is copied there as its page-marked text (`NN-name.pdf.txt`), and an image as itself, which its Read tool opens as a picture. What the chat has left of its **Limit per task** (the task's cap minus Orglet's settled and reserved charges and the estimates earlier Claude Code calls in this run reported) is passed as `--max-budget-usd`, so Claude Code stops itself at that cap. When it does, its result carries `error_max_budget_usd`; Orglet records the estimate it reported, marks the run and the chat **Đang chờ ngân sách** (waiting for budget) and says which limit stopped it and where to raise it: **Giới hạn mỗi task** in the crew's **Thiết lập hội → Giới hạn & ca** or the orglet's **Thiết lập Tí**. Codex and Cursor Agent take no spending cap, so this can only happen with Claude Code.
- Codex runs `exec --sandbox read-only --ignore-user-config --ignore-rules --ephemeral` with apps, browser use, computer use, web search, image attachment (`view_image`) and its shell tools disabled; project instruction loading is set to zero bytes. Orglet sends the permitted text sources in the prompt instead (256 KB per file, 1 MB total, no Parquet), a PDF as its page-marked text. The chat's images go in as hash-checked copies attached with `--image`, never through `view_image`, which would open any path the model names ([why](capabilities.md#pdfs-and-images)). Codex therefore has no file or command access at all.
- Codex's structured-output API requires all nested object properties to be required. For a source-only answer, Orglet asks for one strict string field containing the report JSON, parses it, then validates the original report contract before saving anything. This avoids rejecting optional nested fields such as `review.checks[].processIds` at request time. A signed-in Codex CLI 0.155.0-alpha.9.2 completed source-only and tool-loop trial turns with this path; that does not establish native CLI containment across other versions.
- Cursor Agent runs `agent -p --mode=ask --sandbox enabled --trust --workspace <task-copy> --output-format json`. Orglet never passes `--force` or `--yolo`. The report JSON schema is embedded in the prompt and validated again by core.
- Gemini CLI runs with none of its own tools, and gets the permitted text sources in the prompt the way Codex does, under the same size limits, PDF text included. It gets no images: the only way in is an `@path` reference, which needs the file tools its lockdown removes, so its prompt says it cannot see them. The flags, the settings file and the variables that hold it there are in [Gemini CLI lockdown](#gemini-cli-lockdown) below.
- No Orglet budget reservation is made and nothing is charged to a connection or crew monthly budget. Usage counts against the harness's plan or account; the cost estimate a CLI reports is shown in activity and counts toward that chat's Limit per task, nothing else. Runs share the per-provider concurrency setting and stop after 15 minutes. Cancel kills the process tree. When a CLI exits without a result, the saved error keeps the end of what it printed to stderr (up to 600 characters, colour codes removed); if the executable found at detection is gone by the time the run starts, the error names the path and points at **Rescan**. A source-only harness run is one step: pausing takes effect before it starts, not inside it.
- Orglet cannot see which files Claude Code or Cursor Agent actually opened, so its reports carry that limitation.
For a workspace, team, web or dataset-tool run, each CLI invocation returns one structured tool request. Core validates the request against the tool catalog and current grants before executing it. Claude Code has an empty native tool list; Codex uses the restrictions above; Cursor gets native-tool deny rules in a fresh call directory; Gemini CLI gets its lockdown settings file in a fresh call directory. Pausing between tool steps saves a checkpoint. Reported CLI cost estimates reduce subsequent call allowances and survive resume, but remain separate from API billing; missing costs remain unknown. Fixtures cover all four bridges, while live enforcement inside the CLIs remains unverified. See [agent tools](agent-tools.md) for the supported operations and test boundaries.

Every step of such a run is a fresh CLI process that receives the whole conversation again, so what the conversation carries is what each step costs (COD-183). Three things keep that small:

- Web pages the worker has moved on from go out as excerpts. Before each model step, every page read before the latest two is cut to its first 1,500 characters; its address, title and provenance stay, it is marked truncated, and the worker is told to use what its notes kept and to call `web_read_url` again only for a part it did not note. Each step may carry **notes** beside its tool call (COD-264): the CLI bridge's response has a `notes` field, and an API model's text beside its call counts the same. Up to 2,000 characters a step go back to the model as its own words and are never cut, so what a comparison of several pages needs survives the excerpts; without them a three-site price comparison kept re-reading the same pages until it ran out of steps. Activity says **Đã rút gọn các trang web đọc trước đó** (shortened the web pages read earlier) when a step cut something. The cut is saved with the checkpoint, so a resumed run does not pay for the pages again. Only web pages are cut: source reads keep their text because findings cite them by line, and search results are already small. If a request would still pass the 200 KB limit, every page but the latest is cut (COD-184) before the run fails on size. In the fixture in `tests/integration/harness-step-cost.test.ts`, a twelve-step run reading eleven pages of 24,000 characters sends 808 KB in total instead of 1,188 KB, and its largest step 85 KB instead of 188 KB.
- Claude Code keeps one working directory for the whole run instead of one per call. It writes nothing there and has no native tools to read it with, and the CLI puts the working directory in the fixed prompt it sends the provider (its `--exclude-dynamic-system-prompt-sections` help names cwd among the sections that break prompt-cache reuse), so a directory that changes per step defeats the provider's prompt cache on every step. Whether the cache then hits is the provider's behaviour and has not been measured here for Claude Code. The Anthropic API connection records it on every request: its cache reads and writes are settled apart and shown in Details as the share of input read from cache (see the budget notes below). Codex, Cursor and Gemini CLI still get a fresh call directory, because they write their schema, answer, policy and settings files into it.
- The activity line for each call carries the run's running total: **harness ước tính $0.20 cho bước này, tổng $0.50 trong lượt chạy này** (this step's estimate, and the total so far). When a call reported no estimate, the total is given as a floor with the number of such calls, never as the whole spend. The count lives on the checkpoint with the estimates, so a resumed run continues it.

Orglet does not reuse a Claude Code session across the steps of a run, although `claude -p` accepts `--session-id` and `--resume`. A resumable session needs `--no-session-persistence` dropped, and the CLI then writes the transcript, sources and web pages included, under the account's `CLAUDE_CONFIG_DIR` (`~/.claude` for the default account), where it would appear in the user's own `claude --resume` picker. Pointing `CLAUDE_CONFIG_DIR` at a private folder would sign the CLI out, because that folder is also where it keeps its credentials, and what `total_cost_usd` and `--max-budget-usd` mean for a resumed transcript is unverified, which the Limit per task accounting depends on.

The worker setup and chat Details derive their capability preview from the same task-capability defaults and workspace grant contract used by core. Provider readiness is supplied by main's connection and CLI probes; the renderer does not inspect credentials. A preview describes the next turn, whereas `toolsFor`, `hasCapability` and `WorkspaceGrants.assert` enforce the frozen run plus current policy at every tool call. Dataset and web switches update the task policy; revocation takes effect immediately. See [capability catalog](capabilities.md#what-a-worker-can-do) for the provider matrix and verification limits.

### Gemini CLI lockdown

Read from `@google/gemini-cli` 0.61.0: its bundled docs (`docs/cli/headless.md`, `docs/reference/configuration.md`, `docs/cli/trusted-folders.md`, `docs/cli/cli-reference.md`), its `--help`, and its source. Code: `apps/desktop/src/core/harness/gemini.ts` and `geminiStream.ts`.

Every run is `gemini --output-format stream-json --approval-mode default --skip-trust --extensions none --allowed-mcp-server-names orglet-no-mcp-server [-m <model>]` in a fresh private folder, with the prompt on stdin, which makes the CLI headless. Orglet never passes `--yolo`, `--approval-mode yolo` or `auto_edit`, `--sandbox`, `--include-directories` or `--allowed-tools`.

The CLI cannot be told per run to skip `~/.gemini/settings.json`, and a system settings file named by `GEMINI_CLI_SYSTEM_SETTINGS_PATH` is skipped with only a warning unless an administrator or SYSTEM owns it and every folder above it. What it does load per run, over the user file, is the workspace file `.gemini/settings.json` in its working folder. The working folder is Orglet's, so Orglet writes the lockdown there (refusing a folder that already has one):

- `tools.core: []`: no built-in tool is registered at all, so no file reads or writes, shell, web fetch or search, and no subagents.
- `skills.enabled: false`, because skills register an `activate_skill` tool of their own even with no core tools; `hooksConfig.enabled: false`, because hooks run shell commands; `tools.discoveryCommand`, `tools.callCommand` and `mcp.serverCommand` empty, because each is a command the CLI would run.
- `context.fileName` set to a name no file has, with `memoryBoundaryMarkers: []` and `discoveryMaxDirs: 0`, so no `GEMINI.md` from the home folder or any parent reaches the model; `includeDirectoryTree` and `loadMemoryFromIncludeDirectories` off.
- `tools.sandbox: false`, IDE mode, agents, auto memory, checkpointing and the Gemma model router (which can start a local server) off. A sandbox would restart the CLI in Docker or Podman with the whole prompt on the command line, and with no tools there is nothing for it to contain.

The run's environment adds what a file cannot:

- `GEMINI_CLI_TRUST_WORKSPACE=true`. Workspace settings load only in a trusted folder, and the CLI decides trust while it loads settings, before it parses `--skip-trust`. With the flag alone the lockdown file would be ignored. (`--skip-trust` stays for the later headless trust check.)
- `GEMINI_CLI_NO_RELAUNCH=true`. Otherwise the CLI restarts itself in a child process whose parent ignores SIGTERM, and a cancel on macOS would reach only the parent. Windows cancels already kill the tree.
- `NO_BROWSER=true`, so a missing Google sign-in fails with exit code 41 instead of opening a browser in the middle of a run.
- `GEMINI_SANDBOX`, `GEMINI_SYSTEM_MD`, `GEMINI_WRITE_SYSTEM_MD` and `GEMINI_CLI_IDE_*` are removed: a sandbox choice, a replacement system prompt (or an order to write one to disk), and an IDE connection that adds its open files.

Two things only a flag or the prompt can do. MCP servers from settings and extensions merge across files rather than being replaced, and the settings files' own `mcp.allowed` lists are intersected, where an empty intersection means no limit; `--allowed-mcp-server-names` with a name nobody uses overrides them all, so no server connects. `-e none` loads no extension. And the CLI reads `@path` anywhere in a headless prompt as a file to attach, through its file reader directly rather than its tool list, so every `@` in the prompt goes out as `\@`, the one escape it honours; the model is told to answer with plain at signs, and Orglet restores any `\@` copied into the JSON.

The CLI has no schema flag, so the schema is in the prompt. The answer is the assistant text of the stream (`message` events with `delta: true`); a Markdown fence around it is removed and core validates the JSON. Progress shows the answer's `message` field as it is written; the CLI does not stream its thinking. If a `tool_use` event ever appears, the lockdown did not hold: Orglet kills the process tree at once and fails the run. The closing `result` event carries `input_tokens` and `output_tokens`, which activity shows; there is no price, so cost stays unknown. A `TerminalQuotaError` marks the run `plan_limit`, a `RetryableQuotaError` is a rate limit, and exit code 41, a `FatalAuthenticationError` or an authentication message points at **Harness trên máy** with no Demo fallback.

Sources are inlined for Gemini CLI, as for Codex, rather than read with its own file tools, because those tools would also reach the folders in the user's `context.includeDirectories`, a list a workspace file can only add to.

What remains of the user's setup: `.env` files in parent folders of the run's folder and in the home folder still load, as they do for any Gemini CLI session, and the CLI writes a transcript of each session under `.gemini/tmp` in its folder with no switch to stop it. Not verified: a signed-in run against the real CLI. `tests/integration/gemini-harness.test.ts` runs a fake `gemini` and checks the arguments, the settings file, the variables and the escaped prompt that reach it, the stream parse, the token counts, a tool-loop round trip, the signed-out and quota errors, the stop on a tool request and cancel. That the real CLI honours them rests on the source reading above.

## Teams

Click an **orglet** or a **channel** in the sidebar to open that chat. How find-or-create, Chi tiết jobs, and the orchestrator work: [team-chat.md](team-chat.md).

Identity: newest non-archived `tasks` row with that `workerId` (no `teamId`, no `assignees`, no `routineId`) or that `teamId`, the crew record behind a channel where a lead splits the work (`liveWorkerTask` / `liveTeamTask` in `apps/desktop/src/shared/live-task.ts`; see [Crews are channels](team-chat.md#crews-are-channels)). The first user message calls `createTask`; later messages call `reviseTask` on the same id. Do not create a new task row per send. The chat's cap is the crew's or orglet's current **Limit per task**: core reads it on every follow-up turn, **Thử lại với thiết lập hiện tại** and **Tiếp tục từ checkpoint** (`currentTaskLimit` in `core/service.ts`), so raising it in settings applies to the next turn of an existing chat while a run already in flight keeps the limit it started with. Group chats and scheduled runs keep the limit saved on their own row. The sidebar does not list discrete task rows. Routines stay separate under **Lịch chạy**. `createTask` itself is unchanged, so scheduled work can still insert discrete rows.

Execution for a team is the COD-25 orchestrator (`TeamRunner.run` when `task.teamSnapshot` is set): plan job (synthesizer) → assigned member jobs → one synthesis report. Unassigned members are skipped with a named cancel, not treated as failures. A failed plan does not dispatch members or invent a report. Worker chat is one run with no `stage`. Group chat (`assignees`, `TeamRunner.chat`) stays reachable from search. In a team or group chat, `@name` tags workers; group turns run only the tagged assignees, and Demo team plans assign tagged members (`apps/desktop/src/shared/mentions.ts`).

Long-chat context budget, rolling summary, retrieval and refuse-the-send are specified in [team-chat-context.md](team-chat-context.md); follow-ups still send the existing truncated history window (10 turns, 24 000 characters) until that plan is implemented.

Choose **Kênh mới**, pick the orglets, and under **Cách làm việc** choose **Tí trưởng chia việc**, or use a Research Review or Eris Review template (**Nhập template**). Templates start in Demo mode. The lead may do up to eight parts. In a parallel channel at most two orglets run at once; in a sequential one each passes committed reports to the next. The lead joins the saved reports ([Crews are channels](team-chat.md#crews-are-channels)). Open **Chi tiết** to inspect or export individual role results. Retry keeps successful member results and continues missing roles.

A run that hands in because its steps ran out is not paused: its answer is saved, and in a solo chat without a folder **Tiếp tục** under it starts the next turn from that run's calls and results ([agent tools](agent-tools.md#windows-isolation-backend), COD-257). Use **Tạm dừng sau bước này** to finish the current step and save a checkpoint. **Tiếp tục từ checkpoint** uses the same run and frozen worker/skill settings, including team roles that have not started. A completed final report wins over a pending pause. After restart, interrupted requests are never replayed automatically: a saved response can be processed, but an uncertain request blocks resume. Inspect its retained cost reservation before choosing a new retry. A retry uses current settings for unfinished roles.

New Eris Review templates turn on a dataset check before review. Team settings no longer set it up; a team that has it says so under General, with **Tắt kiểm tra dataset** to turn it off, and a template file can set it with its ID column. It runs local CSV/JSONL/Parquet checks before model roles, including in Demo mode, and saves results and limitations. Set the ID column explicitly in the template; when enabled, pair comparison runs only if the task contains exactly two datasets. It does not infer whether those files are submission/answers or train/test. Existing teams keep their configuration. Preflight supports pause/resume and cancellation; completed checker results are reused. Finished preflight records, including partial coverage, remain fixed for that task. Create a new task to recheck changed inputs.

In a lead channel's settings, choose **Xuất template** to export its saved configuration, orglets and shared skills. In **Kênh mới**, choose **Nhập template** to create a separate copy with fresh IDs. Import preserves provider choices but does not run a task or grant provider/source access. Templates exclude keys, sources and task history. They use versioned JSON, with a 2 MB limit; this is separate from importing Agent Skills directories.

A crew template supports eight members plus an independent lead: at most nine distinct orglets and nine distinct skills, with shared skills deduplicated. Import validates the exact member, lead and skill references before writing any rows. The version 1 format is unchanged; older clients capped at five orglets or skills reject larger templates. Imported packages still need local review, and templates never carry MCP selections or the auto-apply switch.

## Routines and work hours

Choose **Lên lịch cho công việc này** after writing a brief and selecting sources, or open **Lịch chạy → Tạo lịch**. Set a daily or weekly time, a time zone from the list (every IANA zone the app knows, this computer's first, UTC last), a per-task budget and, if the runs should work in a folder, its **Working folder** and level ([routines.md](routines.md#a-working-folder-for-the-routines-runs)). Enabling a schedule requires recurring approval for its selected content and providers. A change to orglet, skill, channel, model or pricing configuration blocks automatic dispatch until you review and save the schedule again.

Orglet checks schedules while the app is open. Closing it or putting the machine to sleep prevents execution. The next due time stays on the calendar. On return, missed occurrences become **one** **Chạy bù một lần** choice (`pending`); they are never queued in bulk and never start automatically. **Bỏ qua lần lỡ** dismisses that choice. See [Routine catch-up](routines.md) for the exact miss threshold (30 seconds), reopen/first-tick rule, and N=1 coalescing. A prior paused, interrupted or budget-blocked task must be resolved before another occurrence runs. Changed or revoked source files block execution. Turning off a schedule does not cancel its current task. There are at most 100 saved schedules.

Times follow the schedule's timezone; the next occurrence is stored in UTC. A nonexistent daylight-saving time is skipped, and a repeated time runs only at its first occurrence. The scheduler polls every five seconds; a gap or delay over 30 seconds is treated as missed work, not permission to catch up automatically.

In a lead channel's settings, set **Số công việc chạy đồng thời** (1–8) and optionally **Giới hạn khung giờ làm việc**. Existing crews default to at most four active tasks. Work hours apply to manual and scheduled tasks. Overnight shifts belong to their starting weekday. At shift end, an in-flight step can finish; no new step starts. Orglet saves a checkpoint and **Bàn giao cuối ca** with committed reports, blockers, next steps and cost state, without calling a model for the worklog. Resume explicitly during a later shift. Lowering concurrency prevents new starts but does not cancel active tasks.

## Knowledge

Open **Thư viện → Knowledge** to save short reusable notes. Each note has a scope: the whole workspace, one team or one worker. A team's notes load only when that team runs, even if one of its workers also belongs to another team. Deleting an orglet or a channel removes the notes and memories waiting for that owner, archives the notes already approved for them, and leaves workspace notes where they are. Archiving the owner keeps its notes, so a restore brings them back. Pinned notes load whenever there is room; unpinned notes load when they share keywords with the task brief, or, with Tacet on this computer, when Tacet says the brief is about them ([memory.md](memory.md#which-notes-load-and-why)). Knowledge is guidance for the model, not source evidence, and cannot grant permissions or raise budgets.

The same store holds **memory**: short lines a worker remembers during a chat (a `remember` tool in the tool loop, a `memories` array in a one-shot harness answer) and carries into its next chats, active at once unless the run had read unvetted content. Each worker's page has a **Ghi nhớ** tab to correct, pin or delete them, and **Thư viện → Knowledge → Ghi nhớ** lists every scope. How it works, the cap, and what reaches a run: [memory.md](memory.md).

A model can suggest up to three notes when it submits a report. Suggestions and notes arriving in an imported team template wait under **Chờ duyệt** and never reach a model until approved; after a turn, the tab on the prompt bar says how many of that chat's suggestions wait and opens them (see the run island above). Editing, approving or archiving creates a new revision. In the note editor the Approve / Refuse (or Save) bar floats in the panel's bottom-right corner in a lane of its own: the fields scroll above it, so none sits under it when the note opens or at the end. Search uses SQLite FTS5 over title, content and tags.

Before its first request, every run freezes the context it will use. **Chi tiết → Context đã nạp** lists the instruction and knowledge revisions loaded and anything left out as a duplicate, over the 12-note/16 KB limit, or unrelated to the brief. Later edits never change a finished or resumed run. Follow-up turns currently send a truncated recent window (10 turns, 24 000 characters), not a rolling summary; the long-chat policy is [team-chat-context.md](team-chat-context.md). Team chat UI (click team → one live thread) is [team-chat.md](team-chat.md). Team templates carry only that team's approved notes; backups carry all knowledge with its revision history.

## Search

Ctrl+K search (COD-267) covers every message the person sent, every answer and report a chat shows, side threads, scheduled chats, chat titles, and orglet and channel names. It runs in the core over SQLite FTS5; nothing leaves the machine.

- **Storage.** `chat_messages` holds one row per message: the person's turn (keyed by `turnMessageId`, so the first message's id is the chat's) or an answer (keyed by the artifact id), with the chat, who wrote it (the answer's byline name), when, `text` as the chat shows it on one line, and `body`, the same text folded to lower case without accents and with đ as d. SQLite's `unicode61` tokenizer does not fold đ, so folding happens in `shared/chat-search.ts` before the text is indexed and before the query is matched. `chat_search` is an external-content FTS5 table over `body`, kept in step by triggers; `chat_messages.id` is an explicit `INTEGER PRIMARY KEY` because the index points at rows by rowid, which `VACUUM` keeps only for such a column. Schema version 18 adds both tables and drops `task_search`, which held first messages only and was never read.
- **Writes.** The row is written in the same transaction as what it indexes: `createTask`, `startSideThread` and scheduled runs index the first message, `reviseTask` each later one, and the runner each answer as it commits (`ChatSearch.indexAnswer`). A report is indexed by its title, summary and findings, a chat answer by its message, both with Markdown syntax removed and source ids read as file names. A crew member's own report is not indexed, since the chat shows the combined answer, and neither are quotes brought in from a side thread (the side thread's answer is) or crew messages that live in Details. Deleting a chat removes its rows, including a charged chat that keeps an empty record of its runs. Chat titles and orglet and crew names are matched when a search runs, so renames need no index work. A restored backup indexes every chat again; a full erase empties both tables.
- **Upgrade.** The migration only creates the tables and, when chats exist, a `chatSearchBackfill` settings row. After the core reports ready, `ChatSearch.backfill` indexes 25 chats per transaction and yields between steps, saving how far it got so a restart carries on. While the row exists, results carry `indexing: true` and the window says a few may be missing.
- **Query.** The query is folded and cut into at most 8 words; each is quoted, so FTS5 operators typed as text are searched as words, and each matches the start of a word. The core reads the 600 newest rows holding every word and the 300 newest holding them as a phrase (`"a b c" *`), keeps each chat's best row (phrase first, then newest), adds chats whose title matches, and ranks chats the same way: phrase matches first, then the newest matching message. It returns at most 50 chats, each with a snippet cut at spaces around the first place the words appear, the matched words marked. Archived chats are included, as before; deleted ones are not. Live orglets and crews whose name matches are returned first; the window opens their chat.
- **Opening a result** reuses the reply jump (`focusMessage`): the chat opens, and once its detail is on screen the message is scrolled to the centre and focused. A kept copy of the chat older than the message waits for the fresh one before giving up.

## Appearance

The interface asks for **SF Pro** first (the owner's pick): macOS supplies it, and anyone else installs it for their own machine. Orglet does not ship it — Apple licenses SF Pro for use on Apple platforms, so it cannot be bundled or redistributed — and the two fonts Orglet does ship stand behind it: **Inter** for the interface and **JetBrains Mono** for code, paths and other technical values. A Windows machine without SF Pro installed therefore draws Inter, which is what that font was designed to substitute for. Both are SIL Open Font License 1.1 and live in `apps/desktop/src/renderer/fonts`, loaded by `@font-face` from the app itself — `index.html` sets `font-src 'self'`, so no font is ever fetched over the network, and the app looks the same on a machine that has neither installed.

**Cài đặt → Chung** can put another family in either role. The picker lists the default first, named after what this machine actually draws: **SF Pro** where it is installed and **Inter** where it is not, so SF Pro is never offered on a machine without it; for code, JetBrains Mono. Inter gets a row of its own only when SF Pro is the default. Then come the suggested families this machine actually has — measured by drawing text in the family against a generic fallback, because `document.fonts.check` answers yes to any name — and **Phông khác…** takes a family typed by hand. The "(default)" note shows beside the default in the open list only; the closed picker names the family alone, so it fits the settings column's 210px in every language. A family name is letters, digits, spaces, periods and hyphens only (`shared/fonts.ts`), because the name is written into a CSS custom property; anything else is refused and the bundled font stays. Each option is drawn in the font it names. Under the interface row a card marked **Preview** shows one sentence in the interface font with Vietnamese diacritics; under the code row two cards show the same short snippet in the code font on a light card and a dark card side by side (stacked in a narrow window), with line numbers, the source viewer's own syntax colours and one removed/added pair, so the diff colours show too. Each card carries its own theme (`.theme-light` / `.theme-dark` in `styles.css` put one palette on a subtree), so both are visible whichever theme the app is in.

The choice is stored like the accent colour and applied to `--font` and `--font-mono` on the root element, so it reaches every surface at once and survives a restart. A picked family that is missing falls through to the bundled font, never to blank text.

The accent colour (**Màu nhấn**) defaults to `#4473d3`, which carries white text at 4.53:1 (COD-250; the earlier `#4f7fe0` gave 3.86:1, and a workspace that saved it reads the new blue). Whatever the person picks is kept, and what is drawn on it follows from it (`shared/accent.ts`, set on the root by `App.tsx`): `--accent-ink`, the text on a primary button or a count badge, is white where white reaches 4.5:1 and a near-black otherwise (pure black in the narrow band of mid-tones where even the near-black falls short). `--accent-text`, the accent used as text such as a @mention, is the accent moved toward the theme's text colour just far enough to reach 4.5:1 on a mention's wash over the accent-tinted bubble the person's messages had before COD-365, worked out separately for the light and the dark theme. That is darker than anywhere a mention shows now that messages sit on the page, so the result still holds. The orglets' own palette keeps its blue; in the accent swatches it is replaced by the default.

## Loading

Orglet is local: the renderer asks the core over IPC and the core reads SQLite, so almost nothing should ever need a visible wait. The rules the app follows (COD-218), so new work keeps them:

- **The shell draws on the first frame.** `Startup.tsx` renders the same frame the app uses — the area rail with disabled tiles, the sidebar at the width the person left it with the shape of the direct-message rows, the user panel, the main column with the prompt bar in place — and the workspace fills it in when it lands. The 3D orglet does the waiting where the chat's face will be. A root-level wait never replaces the window with a centred spinner or a blank page.
- **Fetch on hover, keep what was seen.** `renderer/prefetch.ts` is a small session cache (`SessionCache`: dedupe, a 100 ms dwell, a bounded least-recently-read store, invalidation and pruning) and `renderer/caches.ts` holds one per kind of thing a click opens: a chat's detail and folder grant, a provider's model list, an imported skill's review, a run's diff, a text source's preview, and the About tab's build, updater state and release list. A sidebar row, a search result, a Library row and the Settings button fetch what their click will open while the pointer or focus rests on them; opening draws the kept copy at once and fetches the fresh one behind it. The caches are UI chrome: session memory only, never disk, and never the place where state lives.
- **The core is still the truth.** Money and usage, a harness's sign-in for a run and a folder grant are read again when they matter; a kept chat is dropped as soon as the workspace lists its row with a different answer, input or status (`followWorkspace`), grants and diffs are dropped on every change, and model lists on a connection change or **Dò lại**.
- **No spinners.** A wait that cannot be hidden shows the shape of what is coming: `Skeleton`, `SkeletonText` and `SkeletonGroup` from `packages/orglet-ui`, bars the height of the text they stand in for, sweeping under a second per pass and still (not sweeping) under `prefers-reduced-motion`, with one spoken label per group. Something fetched again behind content already on screen says so in a quiet word beside its title (`Đang dò lại…`, `Đang tải lại…`), never with a spinner. A spinner inside a button is allowed only for a click that takes real time, such as fetching a model list from the provider.
- **Never "not found" while still looking.** The harness tab shows three row shapes until the first detection lands; the empty-state sentence appears only once detection has answered. Errors are shown, never hidden behind a shape.
- **No waterfalls.** A refresh asks for the open chat, the workspace, the connections, the grant and the recovery view in one `Promise.all`; harness detection lands on its own; nothing on the network runs before first paint.
- **The orglet carries the first-run screens (COD-341).** Startup, the first-run account choice and the app are separate trees. `swapScreen` in `renderer/screenTransition.ts` applies the refresh that replaces one with the next inside `document.startViewTransition`, with the root as a cut: nothing on the screen fades or slides. Only the startup orglet moves: it hops from its place on the startup screen to its place on the account choice (crouch, jump, a squash on landing, 380 ms, `first-run-hop` in `styles.css`). The name exists only while a swap runs (`.screen-swap` on the root). Into the app the choice's face goes with its screen and the new chat's own orglet greets with its hop. On the choice the 3D stage does the rest: it glances when the browser opens, thinks while it waits, winces at a failure and smiles for 280 ms (`holdForSmile`) before the choice is saved. Under `prefers-reduced-motion` every swap is a plain cut and there is no held beat.

## Keyboard focus

Focus never falls to the page after something the person did (COD-284). The rules, so new work keeps them:

- **The message box is never disabled while a message is on its way.** Disabling a focused textarea blurs it, so the next words typed went nowhere. The follow-up bar (`FollowUpComposer`) and the empty chat's bar (`send` in `App.tsx`) empty the box the moment a message goes and hold back only a second send (`sendDisabled`). If the call fails, `restoreUnsent` puts the message back in front of whatever was typed since. The empty chat's first message opens a new chat whose bar is a different element, so the words typed while it went and the focus move there through the bar's `prefill`. A new request waiting for the old turn to stop (`pendingStart`) also only blocks sending.
- **Sending keeps focus in the box**, including with the send button or the send options menu, whose button the emptied bar disables.
- **The + menu hands focus to the message box** before the file dialog opens (`MessageBoxFocus` in `SourcePicker.tsx`, provided by `Composer`), so the window gives it back there when the dialog closes.
- **Dialogs return focus to what opened them.** Radix only does that for a `Dialog.Trigger`, and Orglet opens its dialogs from state, so the kit's `useReturnFocus` remembers the focused element when a dialog opens and focuses it again when it closes, but only when focus would otherwise be lost (on the page or inside the closed dialog): a link inside a viewer that closes it and focuses its target, such as a report's checker link, keeps that focus. `Drawer`, `TabbedDialog` (Settings and every tabbed editor), `Confirmer`, `Viewer` and the forward picker use it.
- **Details takes focus when it opens** (its heading) and gives it back to what opened it when it closes with focus inside. A link that opens Details on one message or attempt focuses that on a later frame.
- **The prompt bar shows focus with its own line** (owner, 2026-10-05): focus inside it darkens the bar's one-pixel outline (`--bar-line-focus`) and deepens its shadow a little, and the live tab docked on it follows. It no longer turns the focus colour while typing, which read as a different control; the caret says where the keys go. A button inside the bar keeps the usual ring.

## What is running and the queue

The **Running** view (COD-244) is built by the core, not guessed by the window. The `workspace` command returns it as `running` (`runningView` in `core/orchestration/running.ts`), so it arrives in the same snapshot as the tasks the sidebar draws, and a `changed` event refreshes both. The step each run is on comes from the same `progress` events the chat uses; the window keeps the newest one per run from launch (`renderer/runProgress.ts`).

A chat is listed exactly when its status is `queued`, `running`, `pausing`, `paused` or `waiting_budget`, which are the statuses the sidebar draws as working or waiting, or when it is `waiting_input` with an open question or MCP approval (`runningListsTask` in `shared/running.ts`), and every listed chat has at least one row. A chat waiting for input for another reason, such as evidence a review asked for, has no run to go back to and is not listed. A run stopped on an MCP approval (COD-241) is one row under **Waiting for you**, named after the tool and server, with only **Open chat**: the answer card in the chat resumes the same run. The footer button carries two counts (COD-287): `runningCount` for what is under way or will start by itself, and `waitingForPersonCount` for the rows under **Waiting for you** (`waitsForPerson`: a paused chat, one waiting for an answer or approval, and one stopped at its budget), drawn in the accent with the pause sign. A paused crew's row is the run that stopped mid-step with a checkpoint, or else the run whose step came last before the pause (`pausedAfter` in `shared/paused-turn.ts`, which reads the activity lines: every run of a crew turn is created with one line, and a pause marks the runs that had not started as paused too), so it names the member who worked last rather than the next one waiting; the chat signs the paused turn the same way. Rows come from where the core really holds work back, and none of these changes the order or the limits:

- **Provider slots.** `ProviderSlots` (`core/orchestration/slots.ts`) is the per-provider queue behind **Settings → Concurrent requests per provider**. It records which run each waiting request belongs to and when it joined, and `waiting()` returns the line in the order it is served, with how many wait ahead for the same provider. It fires a change when a run starts or stops waiting, and not when a free slot is taken at once. The wait is per model request, so a run can wait again between steps. Every custom connection has its own line. Demo runs never take a slot.
- **Crew member slots.** A channel where the lead splits the work (a crew) runs at most two members at once (one for a sequential one) and a member whose `dependsOn` teammates have not delivered waits for them. `TeamRunner` keeps what each queued member and the combining step wait for (`crewWaits`, `planWaits` in `core/orchestration/crew-waits.ts`): the plan, a named teammate, a member slot with its place in line, or the members. In a sequential crew each member works from every earlier member's result, so the members before it that have not delivered are the teammates it waits for (COD-257; it used to read as a member slot). It is written as the runner decides, never read back by it.
- **Channels.** Orglets answer one after another; the ones still to come are listed with their place, before their runs exist (keyed by chat and orglet).
- **A new message** sent while a turn is still stopping waits for that turn (`pendingStart`).
- **Budget.** A chat stopped at its **Giới hạn mỗi task** is `waiting_budget`: the core lists it as a queued row waiting for `budget`, the view shows it under **Waiting for you** and counts it there, since it goes on only after the limit is raised and the chat resumed.

A lead channel's **Số công việc chạy đồng thời** is not a queue: a turn over it is refused when sent, so it never appears here.

Cost so far is what was recorded for that run: the ledger for a paid API or for a custom connection with a known price, including a local one at $0 (**At least** while a request's cost is unknown), the CLI's own reports for a harness tool loop, and $0 for Demo and Ollama. A one-shot harness run (Claude Code, Codex, Cursor Agent, Gemini CLI), a plan-billed API (OpenCode) and a custom connection with no price show **Cost unknown** instead of $0. Each custom connection is its own provider (`custom:<id>`) with its own slots, and its row names it by the name you gave it. Pause, resume and stop call the existing `pause`, `resume` and `cancel` commands for the row's chat. Cancelling a run still in the provider line removes it from the line before it is sent.

## About and updates

**Cài đặt → Giới thiệu** is the last settings tab. It shows the app mark as the 3D orglet (`AboutFace` in `AboutSettings.tsx`: `Orglet3D` in the logo's colours, following **Màu logo**, on the shared face stage): it greets when the tab opens, follows the pointer, and a click, Enter or Space plays the smile with a hop; under reduced motion the stage keeps it still. Beside it are the version the running build reports (`app.getVersion()`, which Electron reads from `package.json`), and a details line with the Electron, Chromium, Node and SQLite versions, the operating system and architecture, and how the build was installed: with Setup (Squirrel), as a ZIP, as a macOS app, as a Linux ZIP, or run from source. **Sao chép** puts those lines on the clipboard for a bug report. Under it are the links to the website, GitHub, Discord, X and Threads. The renderer names a link by key; the main process holds the five addresses and opens them in the system browser, so nothing shown in the window can choose where a click goes.

**Có gì mới** lists the last ten GitHub Releases, newest first, each as its version, its date and its notes rendered as Markdown, with the running version marked. The notes are cut to what changed by `releaseHighlights` (`shared/release-notes.ts`), which drops a first line `**Orglet X.Y.Z** for …`, the paragraph before the first heading that starts "If you run" (or "If you installed"), and everything from a `Before you install` heading on; anything it does not recognise stays, and the releases themselves are not edited. Links show their text only, since the app does not open them. Only the newest is open; **Hiện N bản cũ hơn** expands the rest. The main process fetches the list from GitHub's releases API with no identifying headers, validates it, and keeps the last good copy in `changelog-cache.json` next to the database. A fetch is reused for an hour; the reload button forces one. Offline, the tab shows the saved list and says when it was fetched; with nothing saved, it says the list could not be fetched.

**Kiểm tra cập nhật** is the built-in Electron updater on the feed `https://update.electronjs.org/codepawl/orglet/<platform>-<arch>/<version>`, a free service that reads this repository's public Releases. It works only where Squirrel can replace the app:

| Build | What the row says |
|---|---|
| Windows, installed with Setup.exe | Checks, downloads and offers a restart |
| Windows ZIP | Cannot update itself (no `Update.exe`); links the releases page |
| macOS, signed by CI | Checks against the feed (the Release has to carry a `-darwin` ZIP for an update to exist) |
| macOS, unsigned local make | Cannot update itself; links the releases page |
| Linux ZIP | Cannot update itself; links the releases page |
| `pnpm dev` | Cannot update itself |

The row shows one state at a time: not checked yet, checking, up to date with the time, downloading, ready with the version and a **Khởi động lại** button, or the error the updater reported. **Tự động cập nhật** (on by default, stored with the other settings) checks 30 seconds after the window loads and every four hours while the app stays open, downloads in the background, then raises a notice; if the person does not restart, the next launch already uses the new version, because Squirrel unpacks it as soon as it is downloaded. Turned off, the app checks only when the person clicks **Kiểm tra**. The first launch after Setup (`--squirrel-firstrun`) skips the startup check so it does not race the installer; the interval still runs. A check that is already running, a download, or an update waiting for a restart makes a scheduled or clicked check do nothing. The state lives in the main process and is pushed to the window over the typed bridge.

The main screen shows an update in two places (COD-304), both read from the same state as the About row. Beside **Cài đặt** in the sidebar, a grey arrow appears while a new version downloads (a click opens this tab), and once it is downloaded a small **Cập nhật** button in the accent tint restarts into it; its tooltip names the version. Nothing shows there while the app is up to date, checking, after a failed check, or on a build that cannot update itself. The download also raises one toast with **Khởi động lại**, kept in **Thông báo**: while that update still waits, its row there carries the same restart button, and afterwards it stays as a plain record. Every restart path asks first when runs are still working, since quitting interrupts them (they come back interrupted, to review and resume). Restarting calls Electron's `quitAndInstall`: Squirrel's `Update.exe --processStartAndWait Orglet.exe` waits for this process to exit, then starts the newest `app-x.y.z`.

The updater writes one line per event to `updater.log` in the data folder (`%APPDATA%\Orglet` for a Setup install): the feed it uses, when it will check, why each check ran (startup, interval or manual), and what came of it, including the engine's whole error text (the About row shows only its readable part: on Windows the message of the exception inside Squirrel's stack trace, such as "The remote server returned an error: (404) Not Found."). The file keeps its last 64 KB. Squirrel logs its own side in the install folder (`%LOCALAPPDATA%\orglet`), one file per kind of `Update.exe` call: `Squirrel-CheckForUpdate.log`, `Squirrel-Update.log` (download and unpacking) and `Squirrel-ProcessStart.log` (the restart). To try the whole loop without a release, see [windows-release-gates.md](windows-release-gates.md#proving-an-update-on-your-own-machine).

Builds 0.2.3 and earlier have no updater and never learn about a newer version; the first release that carries it is installed by hand. For what a release has to include, see [windows-release-gates.md](windows-release-gates.md#updates).

The same tab has the row for the `orglet` terminal command. The main process listens on a named pipe (Windows) or a `cli.sock` socket in the data folder (macOS, Linux), checks a token it writes to `cli-token` on every start, and answers only `status`, `list`, `send`, `read` and `open`; `send` runs the composer's own `createTask` or `reviseTask`. The packaged build ships the script as `resources/orglet-cli.cjs` with `resources/bin/orglet.cmd` and `resources/bin/orglet`, which run it with the app's executable as Node. On a packaged Windows build **Thêm vào PATH** writes `%LOCALAPPDATA%\Orglet\bin\orglet.cmd`, rewritten on every start of the copy it points at so it follows updates (another copy never rewrites it, COD-296), and adds that folder to the user Path; macOS shows the `export PATH` line instead. From source, `pnpm orglet` runs the script `pnpm dev` builds. Details: [cli.md](cli.md).

## CodePawl account

The optional account (COD-337, user page [account.md](account.md), design [account-sync-design.md](account-sync-design.md)) lives in the main process, `main/account.ts`, which imports nothing from Electron so the tests drive it against a fake identity server.

- **Service.** `https://accounts.codepawl.com` by default. `ORGLET_ACCOUNTS_URL` points a run at another one, such as a local service at `http://localhost:8787`; only https, or http on this computer, is accepted. The issuer is `<base>/api/auth`, with `oauth2/authorize`, `oauth2/token` and `oauth2/revoke` under it, and `GET <base>/me` answers who is signed in.
- **Sign-in.** OAuth 2.1 authorization code with PKCE (S256) and a random `state`, client `orglet-desktop`, scopes `openid profile email offline_access`, resource `https://sync.orglet.codepawl.com`. The system browser opens the authorize page; it comes back through `com.codepawl.orglet:/auth/callback` (RFC 8252), which reaches the running app as a second instance's argument on Windows or as `open-url` on macOS. A callback whose `state` or `iss` does not match the sign-in in progress is dropped and the sign-in keeps waiting; after 10 minutes it stops.
- **Tokens.** The refresh token, with the profile last read, is one `safeStorage`-encrypted file, `account.credential`, beside the API keys. The access token (15 minutes) stays in memory. Refreshes are single-flight: the service rotates refresh tokens and treats a rotated-out one sent again as theft, revoking every device, so two callers share one request and the new token is saved before anything else runs. A refused refresh (`invalid_grant`) turns the account `expired` and keeps the profile; a network failure leaves it signed in.
- **Sign-out** deletes the file first, then asks the service to revoke the refresh token, best effort.
- **The window** gets only `AccountState` (`status`, email, name, plan, entitlements), parsed strictly on the way out, through `accountState`, `accountSignIn`, `accountCancelSignIn`, `accountSignOut` and the `orglet:account` event.
- **The first-run choice** is the `accountChoice` setting in SQLite. Only a database created by this build starts undecided; one from an older build has no record and reads as local, never asked. The choice is not in a backup.

A development run (`pnpm dev`) and a ZIP copy do not register the scheme, so the browser cannot hand the sign-in back to them; a Setup install registers it on every start.

### Account sync

Desktop replication (GH-482, design [account-sync-design.md](account-sync-design.md), server [services/sync](../services/sync/README.md)) runs while Orglet is open and an account is signed in.

- **Server.** `ORGLET_SYNC_URL` names it; only https, or http on this computer. There is no default: CodePawl's sync service (`sync.orglet.codepawl.com`) runs as a private trial, so a build without the variable never syncs and the row says sync is coming. The access token is the account's sync resource token.
- **Who does what.** `main/sync-transport.ts` holds the token, every request, the hint socket and the timers; it imports nothing from Electron. `core/storage/sync-replica.ts` holds SQLite: which accounts this computer joined (`sync_accounts`), the cursor, and which record envelopes the server is known to hold (`sync_confirmed`). Main asks the core through one internal `syncReplica` command that the window's command list does not have. Every action names the account context (account key and sign-in generation); main checks it before each request and before the core applies a reply, and the core refuses a context that no longer matches, so a reply that lands after a sign-out or an account switch changes nothing.
- **Joining.** The app starts the transport with `joinsOnItsOwn` (owner, 2026-10-04): a signed-in computer joins without being asked and merges, and one whose only data is its untouched Researcher drops that seed when the account brings orglets. The one case that waits (`link_required`) is a computer erased on purpose, where the replica's state says `held`; **Sync** in Settings → Account (`syncStart`, three seconds of rest after a press) joins it again and otherwise runs a cycle now. Without the option the transport keeps the earlier rule, which the tests still cover and no screen reaches: any data waits for the person (GH-484): `syncPreview` reads the account's snapshot and answers counts only (orglets and chats on each side, and how many items are local-only), sending nothing; `syncStart('merge')` joins as is, and `syncStart('replace')` first runs the core's `replaceWithAccount`, which refuses while anything is running, saves `VACUUM INTO <database>.before-replace-<time>.bak` (newest only) and then erases the workspace as Erase all data does, minus Tacet's files. A failed copy erases nothing and leaves sync off. Erasing keeps a held row for each joined account, so the account does not return without that click, and keeps the device id, because the server ties a sign-in to one device.
- **A download** stages every snapshot page in main, then hands the records to the core in dependency order, saves the cursor and queues every local record whose current envelope the server lacks. A `cursor_reset` (history pruned, or a privacy withdrawal moved the epoch) downloads again.
- **Sending.** The outbox goes out in batches of at most 100 records and under the 8 MiB request limit, ordered so a record's dependencies go first (an orglet before its skill, a chat before its turns, a run before its answer). A batch keeps its record ids until acknowledged, so a lost reply is resent and the server answers it from its receipts. A refused upload (account full, a record the server will not take) holds sending for 10 minutes while downloads continue. A row over the 2 MiB record limit is never sent and is counted on screen. Local changes are sent 5 seconds after the first one and at most once a minute while they keep coming.
- **Receiving.** A pull runs only after a hint on the socket, a reconnect or the window coming forward. The socket carries cursor hints only; it is replaced when the server closes it as its token ends, and after 16 minutes at the latest. A lost connection retries after 5 seconds, doubling to 5 minutes.
- **Limits on the server** (GH-484). The service answers `429 rate_limited` past 600 requests per 10 minutes, 60 file uploads per hour or 10 new devices per day for one account (deployment settings; see the [service README](../services/sync/README.md#rate-limits-and-the-audit-log)). The transport handles it like a lost connection: the status shows offline and the usual backoff retries. Withdrawals and deletions are never limited.
- **Conflicts** (GH-484). A conflict is two or more revisions of one orglet, skill, crew or note at the entity's highest generation with different content (`core/storage/sync-conflicts.ts`, read from `sync_revision_ids`). Sync has already selected the later one by clock. `syncConflicts` lists them with both texts, which one is current and which computer wrote each; `resolveSyncConflict` writes the chosen revision's content as the next local revision through the ordinary revision path, so it takes the next generation, syncs like any edit and ends the conflict on every computer. The older revisions stay, frozen run snapshots are untouched, and a choice made against a generation that has since moved is refused.
- **Files** (GH-483). Only Orglet-owned copies sync: a saved version under `edited-sources/`, at most 25 MiB (`SYNC_FILE_BYTES`). A source record is queued only once a saved turn names the file, because the server takes a file's owner from the turn that carries it; a version nobody sent yet waits without blocking other records. After a push, main reads each unsent version, checks its size and SHA-256 against the record, and `PUT`s it to `/v1/files/<source id>`; `sync_files` records what was settled. A download happens only on the person's click (`syncDownloadSource`): the core checks that the chat owns the source, that it is not revoked and has no file here, main `GET`s the bytes, and the core checks size and SHA-256 again before writing `edited-sources/<id>/<name>` through a `.part` file and a rename. The folder comes from the source id and the name is reduced to a file name. A sign-out or account switch during the download keeps nothing.
- **A new sign-in on the same computer** has a new grant while the server still ties the device to the old one; the transport releases its own device slot once and registers again.
- **The window** gets `SyncStatus` only (state, a pause reason, the last sync time and a count of oversized changes), parsed strictly, through `syncState`, `syncStart` and the `orglet:sync` event.

`tests/integration/sync-transport.test.ts` runs two and three real SQLite workspaces against the service's account object in a local Worker runtime; the Windows CI job installs the service first and sets `ORGLET_REQUIRE_SYNC_SERVICE=1` so a missing install fails there instead of skipping. Those tests use the service's synthetic-identity test entry. `tests/integration/sync-production-entry.test.ts` runs the service's production entry instead, reached over loopback HTTP with the transport's own `fetch` and WebSocket and with EdDSA tokens the Worker verifies against a JWKS it fetches from its issuer (the test stands in for the issuer only): two computers, a hint over the socket, a file as raw bytes, and refusals for another audience, client, missing entitlements or signing key. Neither covers a deployed server or a sign-in at the real identity service.

### Usage analytics

A signed-in account sends usage statistics and error reports (COD-344; what is sent, in the user's words: [account.md → Usage statistics and error reports](account.md#usage-statistics-and-error-reports)). The pure part is `shared/analytics.ts` (the whitelist, the scrubber, the queue limits, the request split and the gating); the sending is `main/analytics.ts`, because only main holds the access token. Nothing imports Electron, so `tests/integration/analytics.test.ts` drives it with a fake fetch.

- **Endpoint.** `POST <accounts base>/v1/analytics`, the same base as sign-in (so `ORGLET_ACCOUNTS_URL` works), with `Authorization: Bearer <access token>` and a JSON body `{ app: "orglet", appVersion, platform, installId, events: [{ name, at, props }], errors: [{ at, kind, message, stack? }] }`. At most 100 events and 20 errors per request and 64 KB per body; a larger queue goes as several requests. `202` removes what was sent; `400` and `413` drop that batch; `401` stops sending until the next sign-in; `429` waits for `Retry-After`; a network error or `5xx` backs off from 30 seconds, doubling up to an hour.
- **Events.** Each is a Zod schema with `.strict()` props, so an unknown event or prop is dropped before it is queued. Props are enums, buckets, versions and provider or model ids only:

  | Event | Props | Recorded by |
  |---|---|---|
  | `app_started` | `version`, `platform`, `arch`, `locale` (the app language), `installKind` | main, at start |
  | `update_installed` | `from`, `to` | main, at the first start of a new version (`lastVersion` in `analytics.json`) |
  | `chat_turn_sent` | `chatKind` (solo, crew, group, side, schedule), `connectionKind` (demo, api, harness, custom), `provider`, `model` | the core, after `createTask`, `reviseTask` or `startSideThread`; a custom connection is only `custom`, never its id or model |
  | `run_finished` | `outcome` (completed, partial, failed, cancelled, interrupted), `durationBucket`, `stepCountBucket` (tool calls recorded), `chatKind` | the core, from `Store.onRunStatus`, once per run |
  | `feature_used` | `feature`: tabs, rail, side_thread, schedule, browser, desktop, mcp, file_viewer, file_edit, forward, cli, send_to, tacet | main from commands (`featureForCommand`), the `orglet` pipe and Send to; the window for tabs (two or more open), folding to the rail and opening the file viewer. Once per feature per app session |
  | `setting_changed` | `setting`, and `value` only for an enum or on/off setting | main, comparing a `settings` save with the settings it last saw |

- **Errors.** Main's `uncaughtExceptionMonitor` and `unhandledRejection`, the core's `uncaughtExceptionMonitor` (posted to main), the window's `error` and `unhandledrejection` (sent through `reportError`), and failed runs as `run_failed` with the run's error code only, never its message. `scrubText` turns the home folder (both slash directions, any case, `file://` URLs) and the user name into `~`, removes emails and everything after `?` or `#` in a URL, and masks `sk-`, `ghp_` and similar key prefixes, bearer values, JWTs, hex of 32 or more characters and long mixed base64 runs. The message is cut to 500 characters and the stack to 4000.
- **The service's item rules.** The service refuses a whole request when one item is invalid, so before each send every item is checked against `WireEvent` / `WireError` (the service's own rules: event names `^[a-z][a-z0-9_]{1,40}$`, prop keys `^[A-Za-z][A-Za-z0-9_]{0,39}$`, at most 12 props of a string up to 120 characters without control characters, a number or a boolean; error `kind` 1 to 100 characters) and against its time (not older than 30 days, not more than 5 minutes ahead). An item that fails is dropped on its own and the rest go. The token is the account's access token, the same one `/me` takes. The service allows 60 requests per account per hour, refused ones included, which the 5-minute flush stays well under.
- **Queue.** In memory and in `analytics-queue.json` in the data folder, at most 500 events and 50 errors, the oldest dropped first. It flushes every 5 minutes and once more at quit (at most 3 seconds). Signing out or turning the switch off deletes it.
- **Install id and switch.** `analytics.json` in the data folder holds a random `installId` (never a hardware id), `enabled` (default on) and `lastVersion`. It is outside SQLite, so no backup carries it. The window sees only `{ enabled }` through `analyticsState` and `setAnalytics`, and can name a feature (`reportFeature`) or an error of its own (`reportError`); it never sees the install id, the queue or the token.
- **When nothing is recorded.** Without a signed-in account (an expired sign-in counts as signed out), with the switch off, with `ORGLET_ANALYTICS=off`, in tests and smokes (`VITEST`, `NODE_ENV=test`, `ORGLET_SKIP_ACCOUNT_CHOICE`, `ORGLET_DESKTOP_TEST`, `ORGLET_SMOKE_DATA`, `ORGLET_TEST_SANDBOX`), in an updater test build, and in any unpackaged run such as `pnpm dev` unless `ORGLET_ANALYTICS=on`.

## Deleting data

**Cài đặt → Dữ liệu** removes what the app has kept. Every deletion refuses while a task, routine or checker is running, runs in one transaction, and reports what it actually removed.

- **Xóa lịch sử trò chuyện** deletes every chat through the same path a single chat uses, so the existing rules hold: a chat that cost money leaves a cost tombstone, and knowledge it taught keeps the artifact it cites. Workers, teams, skills and knowledge stay.
- **Xóa kiến thức** clears the notes in `knowledge`, with their revisions and search rows, including proposals waiting for review. Memory rows in the same table stay.
- **Xóa ghi nhớ** clears every memory in every scope, including memories waiting for review; notes stay ([memory.md](memory.md#deleting)).
- **Xóa nguồn đã nhập** removes source rows. Orglet keeps no copy of an imported file — a source is a path plus a hash — so nothing of the person's own is touched. A source a chat still refers to cannot be removed, because opening that chat reads its sources; it is revoked and its path and hash are dropped instead, which leaves the app unable to read the file and the chat still able to open.
- **Xóa toàn bộ dữ liệu** empties every table (`ERASE_TABLES` in `core/storage/erase.ts`, children before parents) and seeds the workspace again with the Researcher and its skill. It asks the person to type `Orglet` first. An integration test compares that list against `sqlite_master`, so a new table cannot be forgotten.

API keys are not in the database — they are encrypted in the credential store beside it — so no deletion here touches them. Harness account folders belong to Settings → Harness and are not touched either.

## Current limits

In **Cài đặt → Sao lưu và khôi phục**, save a JSON backup of workers, teams, revisions, schedules, task history, reports, checker results, handoffs and costs. Restore validates the format, checksums and references, then adds missing records in one transaction. Existing work, settings and recorded costs stay in place. Imported sources have no file path or read permission; opening one offers **Choose file**, which main's picker hands to the core's `relinkSource` (main-only, like `sourcePath`), and the core takes the file only when its SHA-256 matches the source's recorded hash (COD-281). A source attached on this computer keeps its path and any revocation.

How restore meets what is already there (COD-281):

- **Deleted chats come back.** Deleting a chat that cost money keeps a tombstone: the `tasks` row with `deletedAt`, and its runs with `deletedRunSnapshot` applied (`core/storage/deleted-chat.ts`: no brief, reply, context, preflight or upstream links), so reservations and the ledger still point at them. Restore compares a backup run with a tombstoned one after applying that same function to both, so only the run that was deleted matches, and then the backup's full task and run rows replace the tombstone's. Reservations and ledger rows are keyed by id and the existing ones win, so nothing is counted twice. Runs of that chat the backup does not have (turns after the backup was saved) stay as deleted turns, and the chat continues from the latest of them. A chat that never made a request left no rows and is simply added back.
- **Archived and deleted orglets and crews.** Backups carry the `entityState` setting. Restore applies it to the orglets and crew records it adds; one already here keeps its local state. Older backups have no `entityState`, so what they restore comes back active.
- **A new install's Researcher.** When the workspace holds only the seeded Researcher and its skill, unedited, with no chat, crew, schedule, memory or setting that names them, and the backup brings an orglet that is not archived or deleted, restore removes the seed rows and their revisions in the same transaction instead of adding the backup's orglets beside them.
- **Notifications.** A schedule's run that appears already finished is announced only if it started after the window last looked (with a minute's margin); runs a restore brings in are older and stay quiet.
- **Failures.** A preview or restore that throws shows a native error dialog from main with the reason, and says nothing changed; the restore runs in one transaction. Backups exclude stored API keys, checkpoint context, source file contents and the app-change proposals workers made in chats (`app_proposals`, see [agent tools](agent-tools.md#proposing-app-changes)), but reports can contain source excerpts. Keep the JSON private. Restored schedules are disabled and lose recurring/provider approval; select sources again and review them before enabling. The backup limit is 50 MB.

- Text/code/JSON are read as UTF-8 text, at most 256 KB per file and 1 MB per task. CSV, JSONL and Parquet support local DuckDB checks up to 32 MB per file, 128 columns, a 128 MB query memory limit and a 20-second process deadline. Unsupported or malformed inputs fail explicitly; mixed CSV line endings can be rejected by strict parsing.
- Images (png, jpg, gif, webp, bmp, svg; 20 MB), audio (mp3, wav, ogg, m4a; 50 MB), video (mp4, webm, mov; 200 MB) and PDF (200 MB) can be attached too. They are fingerprinted with a streamed SHA-256 at import. Opening one in the chat shows it in its own viewer (SVG as a picture, never as a document; PDF pages drawn by pdf.js; files over 64 MB open in the default app instead), behind the same task, revoke and hash checks a worker's read passes. Workers read a PDF's text layer, pulled out locally in a worker thread and held to the 256 KB text limit with a `[Page n of N]` line per page, and are shown PNG, JPEG, GIF and WebP images up to 5 MB when their connection can see images (COD-260). Everything else, video and audio included, stays preview-only: the manifest marks it `readable: false` with a note saying why, `read_source` answers with that note instead of bytes, and a local harness gets no copy of it. Which connection sees what, how images travel and what they count against the chat's limit: [PDFs and images](capabilities.md#pdfs-and-images). Symlinks and junctions are refused for every kind.
- Folder intake selects at most 20 supported files and 64 MB total, traverses at most 8 levels and 1,000 entries, and lists excluded items. Hidden files, generated directories and symlinks/junctions are skipped. Review the selected manifest before allowing provider access.
- A task retains the intake exclusion list. Models receive only the excluded count, not those names or contents, and reports disclose that the whole folder was not reviewed.
- Open task sources to run local schema, row/null/distinct counts, column kinds, number ranges, identical rows, ID duplicates, overlap and order alignment ([how the data check reads a file](#how-the-data-check-reads-a-file)). For two files it also compares column names, row counts and IDs present in only one file. Results retain source hashes and checker versions in history. Checks use complete input within the limits; they do not establish semantic correctness, absence of leakage or valid scoring.
- A required team check can demand **Cần đối chiếu hai dataset** evidence. The synthesizer's PASS then stands only when it cites a two-file checker result with an ID column, matching column names and row counts, no null or duplicate IDs and no IDs missing from either file. New Eris Review templates use this for submission/answer alignment, so set the ID column in team settings.
- To recompute one bounded metric, attach two CSV/JSONL/Parquet files to a task and open **Files → More checks → Compare with an answer key**. Select the file to compare, the answer key file, the shared ID column and the two value columns. The checker requires non-empty files, unique non-null IDs, identical ID sets and counts, non-null values, and matching supported scalar column types. Row order does not matter. A missing column or incompatible type produces `unsupported`; empty files, duplicate/null/missing IDs or null values produce `incomplete`. Neither state contains a score. A complete result stores matched/total, accuracy, source hashes, chosen columns and checker version in task history and backups. Run this manual checker before sending a new review turn; an already-started run does not gain new evidence. A team review can require a cited complete `exact_match_accuracy` profile; that PASS means the calculation is available, not that its value meets a threshold or equals the challenge's official metric. Changed or revoked sources must be checked again before a later run cites the result. Custom metrics remain insufficient evidence.
- **Settings → Concurrent requests per provider** (1–8, default 2) caps in-flight model requests per provider across all tasks and teams. Waiting steps show a queue message, hold no budget reservation, and are listed in the **Running** view with their place in line ([What is running and the queue](#what-is-running-and-the-queue)).
- Opening a workspace with a newer build first saves a pre-upgrade copy of the database. See `docs/recovery.md` for rollback.
- The checker runs in a separate utility process without API keys, with extension auto-loading and external access disabled except for its exact temporary source copies. This is process separation, not an OS security sandbox. Normal completion, cancellation and parser failure clean the copies; a whole-app/OS crash can leave temporary copies for OS cleanup.
- A worker has at most six model requests per run, or 24 when it has a workspace grant, with 4,096 output tokens per API request. File edits and commands require separate workspace permissions; commands use the Windows isolation backend. Public web tools require explicit network permission. These grants do not authorize changes to another service. See [agent tools](agent-tools.md) for containment, recovery and harness limits.
- Imported source references are checked against sources the worker read. Workspace-file finding references are minted by core from completed `workspace_read` calls and checked against the same run, grant revision and current private-copy hash before commit. A changed file needs a new read. The saved relative path and hash survive backup; restored grants do not. These checks verify provenance at report time, not whether a model's interpretation is correct or whether the host file remains unchanged later. Unread sources are listed as a limitation.
- New findings include a category, an optional recommendation and checker references. Orglet assigns the finding, writer and run IDs itself. Checker references must belong to that run or its frozen preflight and overlap the finding's cited sources. Reports and backups retain this metadata; older reports stay readable without invented historical IDs.
- Click a finding's source to open its location and preview eligible text, or its checker link to expand the exact result. Provenance is available in a disclosure and Markdown exports. Line-level citations and links between findings are still pending.
- Budgets cover calls through Orglet only. Input is conservatively charged at the uncached rate, except on the Anthropic connection (COD-358). It marks the system prompt, the end of the chat's earlier turns and the latest message for the provider's 5-minute prompt cache, and settles cache reads ($0.20 per million on Claude Sonnet 5.5) and cache writes ($2.50) at their own rates. Its hold before a step prices every prompt token at the write rate plus the step's output cap: 16,000 tokens, or, when the chat's budget left cannot hold that, the most it can hold down to 4,096, and the request asks for exactly that cap (`affordableOutputTokens` in `core/budgets/ledger.ts`). An answer cut off at a smaller cap stops the run with the output-limit reason. Thinking blocks go back with their call while the request before them is unchanged; once the runner shortens an older page or narrows the tools for a wrap-up, they go back as plain notes, since the API refuses a thinking block after an edited prefix. A model that refuses a forced tool choice (Sonnet 5.5, Opus 5.5, Fable 5.1) is sent `auto`, and a reply without a call is asked once to send its answer through a tool. Failed requests, missing usage and interrupted requests keep their original reservation. **Cài đặt → Chi phí & giới hạn → Khoản cần đối soát** lists each one with its provider, chat, run, original hold and reason. Check the provider's usage page or invoice, enter the actual USD amount and confirm that you checked it; enter zero only with provider evidence. Orglet keeps the original hold and a dated adjustment in local history and backups. The task's cumulative cap uses the verified amount; connection and team monthly caps use it for the original request month. An unresolved hold continues to count across months. Repeating the same reconciliation has no further effect; a different amount requires inspecting the saved record rather than silently overwriting it. Orglet cannot independently verify the provider bill.
- Cancelling stops further dispatch. An in-flight request may still cost money. Restart marks interrupted runs explicitly and never silently replays them; retry creates a new run using current worker/skill revisions.
- History, reports and checkpoint context are stored in `%APPDATA%\orglet\orglet.sqlite` on Windows, or `~/Library/Application Support/Orglet/orglet.sqlite` on macOS. Checkpoints can contain selected source text; they are removed on successful report commit, and never sent through the renderer bridge. `safeStorage` protects stored keys (DPAPI on Windows, Keychain on macOS), not against every process running as your user. Workspace records are not encrypted.

## Commands and loopback

A workspace command can start a server, but nothing can connect to it: not the next command, not a child process, not even the process that opened the socket. `fetch('http://127.0.0.1:3123/')` fails with `connect EACCES` (COD-193). This is the sandbox itself, not a missing grant.

Each command runs in a Windows BaseContainer through Microsoft's MXC executor, with the `network` block left out of the policy, which the executor reads as deny for egress, ingress and host loopback. The container is an AppContainer identity under Windows network isolation, where [loopback is blocked by default](https://learn.microsoft.com/windows/apps/develop/communication/interprocess-communication#loopback) and the `privateNetworkClientServer` capability [does not open it](https://learn.microsoft.com/previous-versions/windows/apps/hh780593(v=win.10)). The only switch the executor offers is `network.ingress.hostLoopback: "allow"`, which it implements with `NetworkIsolationSetAppContainerConfig`, the same loopback exemption `CheckNetIsolation LoopbackExempt -a` writes. That exemption is machine-wide for the container identity, [needs administrator rights](https://learn.microsoft.com/windows/apps/develop/communication/interprocess-communication#loopback), and lets the command reach every listener on this computer: your dev servers, databases and other local services, which is exactly what "workspace commands remain offline" promises it cannot. The identity-scoped proxy peer in the MXC 0.8 schema (`processContainer.network.allowedProxyPeer`) needs a proxy that already holds that exemption, and filters scoped to one container ([WFP on Windows](https://github.com/microsoft/mxc/blob/main/docs/sandbox-policy/0.8.0/networking/networking.md)) need elevation or an installed privileged service. Named pipes do not cross launches either: a pipe one command creates is not found by the next, even with the same container id. Measured on 2026-09-23 on Windows 11 26200 with SDK 0.8.0: loopback denied inside one process, between a process and its child, between two launches sharing a container id, and from the host to the container's listener; the container also cannot open a pipe the host owns.

So the sandbox stays as it is. When a command's output shows a loopback connect failure (`EACCES` or `ECONNREFUSED` to `127.0.0.1`, `::1` or `localhost`, or curl's `Failed to connect to`), `workspace_process_status` and `workspace_process_output` carry a `hint` telling the worker that the sandbox blocks loopback and to test in-process: import the app or its request handler and call it directly, or use a test client that injects requests without opening a socket (supertest-style injection, or a Node `http` handler called with a mock request and response). The `workspace_start_process` description says the same before the first attempt. An opt-in, administrator-installed exemption would open all host loopback to the run's commands, so it is not offered; that trade is the maintainer's to decide.

## How the data check reads a file

The data check (COD-297) answers what a person checking a spreadsheet looks for: what each column holds, whether numbers look sane, and which rows repeat. It runs in `profiler/` (`analyze.ts`, `column-checks.ts`) inside the separate checker process, with the same limits as before: 32 MB per file, 128 columns, 128 MB of DuckDB memory, one thread, no temporary files, no extensions and no file access beyond its own copy, and an 18-second interrupt inside the 20-second process deadline.

- **Reading.** A CSV is still read strictly with every cell as text (`all_varchar`). DuckDB's CSV sniffer can guess column types, but it removes a type from a column the moment one sampled value fails to convert, so a single `n/a` turns the whole column back into text and the check could say nothing about the other values ([CSV auto detection](https://duckdb.org/docs/current/data/csv/auto_detection)). Reading text and sorting each value keeps both the column's kind and the count of values that do not fit. JSONL and Parquet keep their own types; a JSONL column with mixed JSON types arrives as `JSON` and is sorted the same way as CSV text. The file is parsed once into an in-memory table and every column query scans that table: before COD-297 each column parsed the file again, so a 14 MB file with 61 columns ran past the deadline, and now finishes in about 3.5 seconds.
- **Numbers.** A value is a number when it matches a plain decimal (`12`, `-3.5`, `1e3`) and converts to a finite double. `TRY_CAST` alone is not used, because it accepts `inf`, `nan` and even reads `inf` as a date. `1,200`, `$5` and `12%` are not plain numbers and count as values that do not fit.
- **Dates.** A value looks like a date when it is written year first (`2024-02-30`, `2024/3/1`, optionally with a time) or day or month first with a four-digit year (`31/02/2024`, `5.1.2024`). It is a real date when `TRY_CAST(... AS TIMESTAMP)` or `try_strptime` with `%d/%m/%Y` or `%m/%d/%Y` reads it; one that looks like a date but reads as neither names a day that does not exist.
- **Kind.** A column is a number column when numbers are more than half its non-empty values, a date column when date-like values are, and text otherwise. The rest are its values that do not fit. Blank cells are left out. Number columns also report the lowest and highest value and how many are negative.
- **Repeated rows.** Identical rows are grouped by a 64-bit hash of every cell, which keeps memory to eight bytes a row. The count is complete; the first ten groups are listed with their first ten row numbers. When no ID column is chosen and the first column's values are at least 80% different (a month, a date, a name), rows that repeat its value are listed the same way, because a column of categories repeats on purpose. A value whose rows are all identical is left out there, since those rows are already listed as identical. A chosen ID column's repeats are listed too.
- **Row numbers** count the way a spreadsheet shows them: in a CSV the column names are row 1 and the first data row is row 2. In JSONL and Parquet row 1 is the first record.
- **What leaves the process.** Counts, row numbers, and the lowest and highest number of number columns. No data row, sample value or text value is returned, and the column's stored type stays DuckDB's, so the two-file comparison and the exact-match check work as before.

Saved checks from before COD-297 stay readable: their table shows the stored type and an empty range, with no notes under it.

## Structured run logs

In task sources, select one CSV/JSONL/Parquet dataset and choose the metric direction under **Kiểm tra run-log**. Required columns are `solution`, `run`, `split`, `metric`, `status` and `score`; `error_code` is optional. Identifier fields are text. Status must be `completed`, `failed` or `cancelled`; completed rows require a finite numeric score. Keep one metric per file and a unique solution/run/split combination per row. Limits: 10,000 rows, 100 solutions, 200 solution/split groups, 200 error codes and absolute score at most 1e100, within the existing file/time/memory limits.

The checker reports completion/failure counts and per-solution/split mean, min/max and sample standard deviation. It excludes failure/cancellation scores without converting them to zero. Fewer than two completed observations in a group is insufficient evidence for that group's rerun variability.

Public/private ranks use mean completed scores only when both named splits cover the same solutions with completed observations. Ties share competition ranks; public rank minus private rank is the number of places gained. Direction is supplied explicitly, not inferred from the metric name. These are descriptive observations, not a stability threshold or approval. The run-log checker does not rerun solutions, authenticate logs or establish independent trials; the separate exact-match checker does not validate a custom challenge metric.

Results are stored with source hashes and preserved in backups. Model-invoked audits use the trusted `audit_run_log` tool and are included with checker provenance in that run's exported report. Manual audits remain in the task's checker history and backup; they are not retroactively inserted into an earlier model report.

## Agent Skills

Open Library to import a directory containing `SKILL.md`. Orglet validates [Agent Skills frontmatter](https://agentskills.io/specification), keeps references/assets/scripts intact, and requires review before assignment or execution. Imported packages are immutable: edit the original directory and import a new package to change one. Library items show their package identity and local review status.

The limit is 100 files, 200 directory entries, eight path components, 256 KB per file and 1 MB per package. Instructions are limited to 16,000 characters. Windows device names, traversal, symbolic links, junctions and hard links are rejected. YAML aliases, custom tags, duplicate keys and unknown frontmatter fields are rejected with an import error.

Workers can read UTF-8 files from the reviewed package's `references/` and `assets/` through `read_skill_resource`. These are guidance, not source evidence. Binary assets and scripts remain available for inspection/export but are not executed or sent as resources. Package instructions and requested text resources can be sent to the task's approved provider. Tool declarations never grant extra permissions.

Export creates a new named directory and refuses to overwrite an existing one. It adds `orglet.json` when absent, containing `input_schema`, `output_schema`, `required_permissions`, `evaluator` and `version_hash`. This extension is specific to Orglet; unsupported schemas, evaluators and permissions block activation. Backups and team templates retain package files, but review approval stays on the current machine. A team template including packages must still fit its 2 MB limit.

A skill written in the app exports its first non-heading paragraph as `description`, up to 1,024 characters, rather than repeating its name. Write that paragraph as a concrete trigger: what work the skill handles and when to use it. If the instructions contain only headings, export uses a short fallback naming the skill. Editing its instructions creates a new revision and changes the next export's description. An imported package keeps its original frontmatter and resources unchanged; its description is not regenerated.

For a new skill directory, start with this shape and replace each example with the actual task. Include Gotchas for recurring mistakes or real limits, and leave it out when there are none. References already load on demand through `read_skill_resource`.

```markdown
---
name: evidence-review
description: Review attached dataset evidence when checking a submission or verifying a claim.
---

Use when checking a dataset submission or a claim against attached evidence.

## Steps
Read the supplied evidence, run the relevant checks, and report what each check establishes.

## Gotchas
A planned check is not a passed check. If run logs are missing, say which log is needed; do not infer stability.
```

### Alignment check

`pnpm test:alignment` (COD-333) checks alignment by measuring instead of by eye. Besides columns inside one container, it compares the rows led by a mark across a whole message or page (`near-miss`): their marks share one edge or sit a clear indent (12px or more) apart, so two rows from different components cannot end 4px apart unnoticed. It launches the packaged app on a temporary data folder, seeds orglets, a crew with an answered turn, a chat with an answer and four schedules (one per orglet, one per crew, one off, one hourly), all on Demo, plus a crew whose member runs on a local stand-in for Ollama (port 11434) that holds its request, so a turn stays at work; it visits the chat, its menus, the crew chat, that crew chat with its island on the prompt bar (`crew-chat-island`, skipped with a note when the port is taken), the sidebar row menu, Schedules and the schedule editor, an empty chat, the tab strip beside the full sidebar and beside the rail, the rail with the right panel open, the orglet dialog (General, Permissions) and every Settings tab (Account, General, Chat, API connections, Web search, Local harnesses, MCP, Browser, Costs & limits, Data, About), with Account also measured while a sign-in waits and signed in, against a local stand-in for the account service whose sign-in skips the browser. Each screen is measured at 1200×820 and 740×600, light and dark, with reduced motion. Logged-out fixture CLIs and empty CLI config folders keep the harness tab from reading this machine's sign-ins or asking a vendor for plan usage.

The measurements live in `scripts/alignment/rules.ts` (unit tests in `tests/integration/alignment-rules.test.ts`) and run in the window:

| Finding | What it measures | Flagged when |
|---|---|---|
| `centre-line` | In a flex row, an icon, avatar, switch or icon button against the text beside it: its first line, the whole block, or the top of a text of two or more lines | the closest of those is more than 1px off |
| `column-start` | Items of one kind stacked in one column, across containers of the same kind (the meta grids of every schedule card form one set of columns): where their text starts | more than 1px apart |
| `icon-slot` | The same columns: the horizontal centre of each item's leading mark | more than 1px apart |
| `uneven-gap` | Siblings of one kind in a flex row or column | a gap differs from the usual one by more than 2px (a much larger gap is a deliberate push and is skipped) |
| `wrap` | Short labels meant for one line (buttons, tabs, menu items, options, switches, badges, headings, labels; 40 characters and five words at most) | the label takes two lines |
| `clip` | One-line text (`nowrap`) | cut by its box with no ellipsis |
| `overflow` | The page, any panel that scrolls, and anything free to spill | the page or a panel scrolls sideways, or something sticks out past the window's right edge |
| `heading-action` | A panel heading (`.org-panel-heading`): where its last action visibly ends, against the right edge of the content box it heads. A button with a surface ends at its box; a transparent one ends at its label and icon; an icon-only button at its box | more than 1px short of the edge or past it |
| `heading-wrap` | The same headings: a description that wraps while the actions beside it take more width than they show | the description's next word would fit on its first line if the actions were only as wide as they look |
| `family-heading` | Screens of one family (every Settings tab), compared at the same size and theme: the top of the heading's first line, from the top of the tab panel (`[role=tabpanel]`) | more than 1px from the value most screens share |
| `family-edge` | The same screens: the left and right edges of the panel's content box, inside its padding and scrollbar | more than 1px from the value most screens share |
| `family-lead` | The same screens: in list rows that start at the content's left edge with a mark followed by text, the mark's horizontal centre and where the text starts | more than 1px from the value most screens share |
| `island-seam` | The live island's two corners against the prompt bar: the corner's bottom border against the bar's top border (bottom edge and width), its side border against the tab's side border (width and edge), and how far the tab reaches into the bar | an edge or width differs by more than 0.05px, or the tab reaches less than the bar's line plus the typing ring's pixel |

Screens join a family with `family` in `SCREENS` in `scripts/alignment-check.mjs`. Family findings are compared once every screen is measured, so they are printed under a `family` line and added to the report, but the outlined screenshot of that screen does not show them.

Stacked faces (a crew) are compared only with other stacks: they are wider than one face by design. Hidden, zero-size and visually hidden elements are skipped, and so is decorative text inside an `aria-hidden` layer. Where a difference is intentional, put `data-align-ignore` on the element or a parent, either empty (every check) or with the kinds to skip (`data-align-ignore="uneven-gap"`), and say why in a comment next to it.

The check prints each finding with its screen, size, theme, selector path and measured offset, writes `alignment-report.json` and one screenshot per screen with findings, the offending boxes outlined, to a temporary folder, and exits 1 on any finding. Options: `--report-only` (exit 0), `--only schedules,settings-general`, `--language en` (Vietnamese by default), `--all-screenshots`, `--out <folder>`. CI runs it on Windows after the other packaged smokes.

`pnpm build` produces `out/Orglet-win32-x64/Orglet.exe` on Windows, or `out/Orglet-darwin-<arch>/Orglet.app` on a Mac. `pnpm make` writes makers under `out/make`: ZIP + Squirrel Setup on Windows; a ZIP of `Orglet.app` on macOS; a Linux ZIP on Linux. The [latest public release](https://github.com/codepawl/orglet/releases/latest) carries Windows Setup and ZIP. Public Windows 0.2.x installers are unsigned by decision; see [windows-release-gates.md](windows-release-gates.md). macOS CI Developer ID signs when P12 secrets exist and notarizes only when Apple ID or App Store Connect API key credentials exist; see [macos-packaging.md](macos-packaging.md). Linux CI makes a ZIP and starts the packaged app headlessly; it does not prove use on a real Linux desktop. Both workflows are separate from the required Windows `test` aggregator; see [linux-packaging.md](linux-packaging.md).
