## Live Codex project trial

An isolated local stationery pop-up project under ignored `test-results/live-orglet-project-*/` was run through Orglet core with the signed-in Codex CLI, not a fixture adapter. `tests/live/worker-team-project.test.ts` saved the project inputs, SQLite database, per-run events, and exported reports. One worker completed a source-backed plan. A two-member team completed planning, independent source reads, handoffs, both member results and final synthesis. All reported the sellout figures correctly: 510,000 VND sales, 289,000 VND inventory cost, 221,000 VND gross profit and 121,000 VND after the booth fee. Actual demand and omitted costs stayed explicit.

The live tests are opt-in and require a signed-in Codex CLI. In PowerShell, set `$env:ORGLET_LIVE_PROJECT='1'` and run `pnpm exec vitest run tests/live/worker-team-project.test.ts`; it prints the retained directory. For the write/execute follow-up, build the package and native helpers first, set `$env:ORGLET_LIVE_WORKSPACE='1'` and `$env:ORGLET_LIVE_PROJECT_DIR` to that directory, then run `pnpm exec vitest run tests/live/workspace-followup.test.ts`. The follow-up changes the retained sample project, so use a disposable run directory.

The first team attempt failed before dispatch because Codex rejected a strict output schema with an optional `submit_plan.note`. The run stayed failed and produced no success artifact. The CLI bridge now requests a strict tool name plus JSON arguments string for Codex, then validates those arguments against the original tool catalog before execution. A regression test covers optional plan fields; the same live project scenario passed after the fix.

`tests/live/workspace-followup.test.ts` used a new turn in that worker chat, an explicit read/write/execute grant, the real Windows BaseContainer helper and integration broker. Codex read the workspace inputs, wrote `sales-summary.md` in its private copy, started a Node check, observed exit code 0, and Orglet integrated the file before saving the final answer. The retained trace includes ordered events, completed tool-call journal entries, process output and the final artifact. Mailbox events now receive per-run sequence numbers; an integration test covers ordering around ordinary events. No other project files changed.

The retained project was also opened in the packaged Electron app. The team and individual chats and Details opened, both tasks were completed, and the renderer reported no uncaught errors. This check exposed that the team reply's Markdown table appeared as raw pipes. The chat renderer now builds semantic table cells with escaped content and horizontally scrollable styling; a regression test and a second packaged UI run verified the visible table. Screenshots and the UI smoke script are retained in the ignored project directory.

These live runs establish one Codex path on this Windows host. They do not prove Claude Code or Cursor live behavior, provider-side tool suppression, installer behavior, web availability, or reliability across varied tasks. Codex did not report token use or cost, so Orglet's usage fields remain zero/unknown for these runs rather than an actual spend measurement.

The earlier fixture-based UI checks covered packaged permissions, native grant bridge, assignment descriptions and dependency labels, keyboard disclosure, interrupted-attempt recovery with preserved failure history, and backup/restore. Translation checking reported zero missing keys. The retained live-project screenshot and UI smoke above add real Codex content on this host; no installer or narrow-screen visual audit is claimed.

CLI termination failures now have a bounded error path: a failed kill command or missing process closure produces an explicit termination error. Core retains the call directory, records failure even after an abort, and keeps the uncertain checkpoint non-resumable. Fault-injection tests cover both termination errors and runner retention; real Windows fixtures still cover normal descendant cancellation. The Windows package was rebuilt after this cleanup change and its packaged smoke passed.

## Four-role SaaS site trial

`tests/live/saas-team-site.test.ts` created a disposable Tallyloom SaaS sales-site project with a product strategist, visual designer, frontend engineer, QA reviewer and lead, all using the signed-in Codex CLI. The first turn was `partial`: the plan stage could not read the workspace brief and guessed wrong write resources. Core denied the designer's write; QA stayed blocked. The product worker submitted a blocker report without creating its required file, yet its assignment was marked completed and unlocked dependents. The lead's final answer did describe the site as incomplete. The retained first-turn trace, artifacts and partial files are under `test-results/live-saas-team-tcOUaa/`.

`tests/live/saas-team-repair.test.ts` reused that task in a new chat turn with exact file ownership in the request. All requested files were integrated: `product-brief.md`, `index.html`, `styles.css`, `app.js` and `qa-report.md`. The original QA worker and first reassignee each failed at report validation after successful reads/checks; the second reassignee wrote the QA report, and the lead completed the task while preserving both failed attempts. Its final answer incorrectly credited the original QA reviewer for the file, rather than the successful reassigned worker. The retained `repair-trace.json` identifies every actual run. These findings are tracked in Linear COD-124, COD-125, COD-127 and COD-128.

The repair trace includes 54 completed tool-call journal entries and five workspace processes, each recorded as exited with code 0. The two invalid report submissions did not become completed journal effects or successful member runs.

A separate headless Chrome smoke loaded the final local site at 1280px and 390px. It exercised the sample queue filter/status change, monthly/annual prices, FAQ disclosure and mobile overflow; no JavaScript errors or HTTP requests occurred. Desktop and mobile screenshots are retained in the reports directory. This confirms the local static prototype, not a deployed SaaS, signup, payment flow, full keyboard audit or screen-reader behavior. The generated site was not manually edited after the Orglet runs.

The retained database was also opened in the packaged Orglet app. The two-turn team chat and Details loaded with task status `completed` and zero renderer errors. Its screenshot confirms that the final chat reply repeats the incorrect reassignment attribution from COD-128; the UI did not repair that text. The packaged app was closed after the smoke.
